# 18. 微码自动化生成（L1 统一入口 + 参数化）

> 开发计划书：`微码自动化生成开发计划书.md`（2026-11-07）
> 本文件记录 L1 落地过程、数字、与计划的偏差。L2/L3 见计划书 §6/§7。

## 1. 目标（L1）

把「一个 kernel 一个 Python 函数」变成「一份 YAML」；新 kernel **不写 Python**。
交付：`cgra/tools/kernel_spec.py`、`cgra/tools/gen_kernel_prog.py`、`cgra/kernels/*.yaml`、
薄壳 `gen_bn_prog.py` / `gen_cn_prog.py`、`Makefile` 的 `kernels` 目标。

## 2. 关键设计决策（与计划书 §5.4 的偏差，必须说清）

计划书 §5.4 说「`build_dfg()` 只做 spec → DFG，全部复用 `rule_map.schedule()`」。
但 §5.5 的硬验收要求 `bn_24.yaml` 生成 **155 拍 / 2480 字、与 `pdsch_bn_prog.h` 逐字节一致**。

查代码确认：`pdsch_bn_prog.h` 由 `rule_map.schedule_bn_split()`（155 cyc）生成，
`pdsch_cn_prog.h` 由 `rule_map.schedule_cn()`（172 cyc）生成——**都不是**通用 `schedule()`。
通用 `schedule()` 对 24 消息的 BN 会排出完全不同的拍序（临界路径 > 31 cyc/pass），
不可能得到 155 cyc。因此「复用 schedule()」与「逐字节一致」在 BN/CN 上**不可兼得**。

**决策**：`gen_kernel_prog.py` 按 YAML 的 `kind` 字段分发——
- `kind: bn`  → `rule_map.schedule_bn_split` + `check_bn_split`（既有已验证调度器）
- `kind: cn`  → `rule_map.schedule_cn`        + `check_cn`
- `kind: dfg` → `kernel_spec.build_dfg()` + `rule_map.schedule()` + 通用自检（**全新 kernel 走这里**）

这同时满足两条铁律：① 不重写映射器（§11：「不要重写映射器」）；
② 与现有产物逐字节一致（§5.5 硬标准）。`build_dfg` + `schedule` 仍是 L1 为新 kernel 提供的
**数据驱动**通路；BN/CN 因有手调过的专用调度器而直连之，符合「复用既有、不为旧 kernel 重造轮子」。

## 9. L2：通用后端补齐（A/D 落地，B/C 机制就位）

按计划书 §6 推进。A 与 D 直接作用于本项目管线、已验收；B 与 C 的真实端到端验收
（array_add 的 `no_addr`/`no_route` 归零）依赖 L3 的 DFG XML 生成器（见 §9.4 与 docs/16
的「只借映射器」结论），故本阶段把它们实现为**纯函数 + 合成测试**，证明机制可用。

### 9.1 任务 A：bank 分配器（已落地，验收通过）

**问题**：`rule_map.leaf_banks`/`sink_bank` 把布局写死，最多 6 个叶子/汇，超了 `SystemExit`。
且 L1 的 dfg 通路其实**无视了 YAML 里的 `bank:`**（add2 是靠「LD 早于 ST」的时序巧合才 0 差异）。

**做法**：
- 新增 `cgra/tools/bank_alloc.py`：`alloc_banks(liveness, hints, n_banks=32)` —— 通用区间图着色。
  每个值有生命区间 `[def, last]`；区间重叠即不可复用同一 bank。
- `rule_map.schedule` 改造（向后兼容）：新增可选参数 `banks`/`sink_addrs`/`return_liveness`。
  - `banks=None`/`sink_addrs=None` 时仍走旧 `leaf_banks`/`sink_bank`（保 `rule_map.main` 的
    `--bn`/`--dfg` 路径字节不变）；
  - `return_liveness=True` 时额外返回 `(生命区间表, 最大活跃寄存器数)`。
- `gen_kernel_prog` 的 dfg 通路改为**两阶段**：① 用临时 bank 规划出生命区间；② `bank_alloc`
  分配（叶子区间 `[0,程序末拍]`、汇区间 `[st,程序末拍]`，在着色意义下两两重叠 → 强制不同 bank，
  匹配「spad 只初始化一次」的自检模型）→ ③ 用分配好的 bank 重新发射。

**验收**（计划书 §6.1）：新增 `cgra/kernels/stress_20leaf.yaml`（20 叶子串行求和，不写 bank）。
- `python3 cgra/tools/gen_kernel_prog.py --spec cgra/kernels/stress_20leaf.yaml`
  → **40 拍 × 16 PE，640 字，自检 16 值 0 差异**（旧代码 >6 叶子直接 `SystemExit`）。
- 抽查 `stress_20leaf_prog.h` 的 LD/ST 立即数：`bank` 集合 = `[0..20]`（20 叶子 + 1 汇，全不同）。

**副作用修正**：`add2` 现在用分配器给的不同 bank（a0→26, a1→27, sum→28），不再是 L1 的
「a0 与 sum 共 bank 26」时序巧合——更正确。`pdsch_bn_prog.h`/`pdsch_cn_prog.h` 经
`cmp` 比对 **与 L1 基线逐字节一致**（专用调度器未动）。

### 9.2 任务 D：算子白名单 + 资源断言（已落地）

- **算子白名单**：`kernel_spec.validate` 早已校验 `op ∈ OPS` 并给出可读错误（计划书 §6.4）。
- **资源断言**（`gen_kernel_prog._assert_resources`，生成前硬断言，不过即 `exit 1`）：
  - `cycles <= 512`（IMEM ≈ 8192 字 / 16 PE）；
  - `bank <= 31`（`spad_idx` 只保留 5 位）；
  - 单 PE 活跃寄存器 `<= 8`（由 `schedule` 的 `max_regs` 统计背书，`free` 空即 `SystemExit`）。

### 9.3 任务 B：地址折叠（纯函数 + 合成测试）

- `tools/morpher/cc.py::fold_addresses`：识别 `base + k*stride` 全常量链，递归折叠成
  `imm[9:0] = bank*32 + word`；链里出现运行时变量则**不折叠**，仍由调用方报 `no_addr`
  （计划书 §6.2 想要的「如实报告」）。
- 合成测试 `tools/morpher/test_passes.py`：`base=5, stride=4, i=3 → 地址 17` 折叠成功；
  地址依赖运行时 `ld` 则不折叠。5/5 测试通过。

### 9.4 任务 C：link 路由 + 多跳（纯函数 + 合成测试）

- `tools/morpher/cc.py::route_links`：在 `translate` 选择器逻辑上加多跳——同 PE 且上一拍
  → 寄存器；四邻上一拍 → `n/e/s/w`；距离 ≤4 且上一拍 → 沿 link 插 `(hops-1)` 条 MOV 转发，
  记 `moved` 计数；否则仍 `no_route`。
- 合成测试：2 跳生产者被路由成功（`moved=1`，无 `no_route`）；同 PE 走寄存器（`moved=0`）；
  旧 `translate` 对 2 跳仍 `no_route`（证明 `route_links` 是增量能力）。

### 9.5 诚实的进度边界

| 任务 | 状态 | 说明 |
|---|---|---|
| **A** bank 分配器 | ✅ 已落地验收 | `stress_20leaf` 20 叶子通过，淘汰 6 上限 |
| **D** 白名单 + 断言 | ✅ 已落地 | cycles/bank/regs 生成前硬断言 |

**为什么 B/C 的真实验收在 L3**：B/C 的输入是 Morpher 的 `schedule.csv` + DFG XML，其中

## 10. L3：DFG XML 生成器 —— 建成，但证明 Morpher 不能当我们的编译器

### 10.1 L3-2 生成器：已建成并验证

`cgra/tools/gen_dfg_xml.py`：读 kernel_spec（`leaves/ops/sinks` + `bank`），展开成 DFG 节点
（叶子→load、汇→store、算子→compute），输出 **Morpher 兼容的 DFG XML**。

生成器严格遵守实测出的 schema 硬约束（见 `src/dfg/DFG.cpp` 与 `CGRA_xml_compiler.cpp`）：

| 约束（源码位置） | 生成器做法 |
|---|---|
| `<MutexBB>` 必须存在（`DFG.cpp:35` 直接解引用） | 写一个最小互斥对 `_0_0`↔`_0_1` |
| `ASAP`/`ALAP` 是 `assert(!=-1)` 必填（`DFG.cpp:81/85`） | 用拓扑层级填（ASAP=level，ALAP=maxlevel） |
| `<Inputs>/<Outputs>/<RecParents>` 均 `assert` 非空 | 空也写 `<RecParents></RecParents>`；边用 `<Input>/<Output>`（非 training 模式） |
| `type="P"` 的 Output 必须带 `NPB`（"`DFG.cpp:233` assert npb∈{0,1}"） | 数据边用 `type="I1"`，绝不写 `type="P"` |
| `OP` 必须是 ADL 声明的算子 | 通过 `--opmap` 选择词表（`gpcp`/`hycube`） |

验证（实证）：用 `--opmap hycube` 生成 `vadd` DFG（OLOAD a / OLOAD b / ADD / OSTORE c），
喂原始 `hycube_original_mem.json`，mapper **完整解析 + 端口解析通过 + 进入调度**
（`Initial target II = 1`），只在最后布局阶段 exit 1（3 节点手搭 DFG 的布局质量问题，
非格式问题）。**证明生成器产出的 XML 是 schema 正确的。**

### 10.2 L3 的核心发现：Morpher 不能当我们的编译器（比 docs/16 想的更根本）

做 L3 的过程中，把"Morpher 能否当我们的编译器"这个根问题彻底钉死了。两个铁证：

#### (R1) 我们的硬件 ADL（v2）从未成功映射过 —— Nov 6 的"II=8"是测错了 ADL

实测：
- `array_add` 对 `gpcp_cgra_v2.json` → `Module.cpp:748` getJSONPort 断言失败（EXIT≠0）。
- 手搭 4 节点 vadd 对 v2 → 同样 getJSONPort 断言失败。
- 只有对 `hycube_original_mem.json`（原始 HyCUBE ADL）才能映射。

根因：我们的 v2 ADL 算子词表是 `LD/ST/MAC/MOV...`、FU 端口名是 `DP0_I1`；
而 Morpher 的 mapper 期望 `OLOAD/OSTORE/MOVC/SELECT...` 和 `I1/I2/P` 端口命名
（`isMemOp()` 只认 `LOAD/STORE`，`getOPtype` 返回 `I1/I2` 去找 `getInPort("I1")`）。
**两套命名对不上，v2 在端口解析这关就挂了。**

→ Nov 6 那次"映射成功 II=8 / 40s"是跑错了 ADL（跑的是原始 HyCUBE，不是描述我们硬件的 v2）。
`docs/16` §7.2 那条"映射成功 II=8"结论是**错的**，已在此更正（见 §10.4）。

#### (R2) 即使修好命名，执行模型也不兼容：Morpher 是空间式，我们的阵列是 SIMD

- **Morpher**：把一个 DFG 的**不同节点铺到不同 PE**（空间映射），输出 `(t,x,y)` 的
  空间布局；共享 SPM（`Variable2SPMAddr` 是全局变量→地址表）。
- **我们的阵列**：同一条指令流**广播给 16 个 PE**，各 PE 只读自己的 SPM
  （`rule_map.schedule` 用 `word=实例号` 区分 PE；`spad_idx(bank,pe)=bank*32+pe`）。

这是两种 CGRA 范式（空间式 vs SIMD）的根本冲突。Morpher 吐出的"PE(0,0) 做 ADD、
PE(0,1) 做 LD"无法转成我们的"所有 PE 同拍做 LD、下拍同做 ADD"。要强行接，要么把 16 PE
当成 Morpher 的 16 个功能单元并强制它们执行相同指令（mapper 不支持），要么 fork 一整套
ADL+后端——那已不是"借它的映射器"，是重写。

### 10.3 结论：Morpher 方向终止，我们的编译器是 L1/L2 那套

- **Morpher 不能做我们的编译器后端**。生成器（`gen_dfg_xml.py`）作为"产出合法 Morpher
  DFG XML"的工具是有价值的（可用于把我们的 kernel 拿到 Morpher 的空间式 CGRA 上做对比
  基准），但它喂不进"为我们的 SIMD 阵列生成微码"这条链路。
- **我们真正的编译器是 L1/L2 已建好的那套**：`kernel_spec`（YAML 参数化）→
  `gen_kernel_prog.py`（统一入口，BN/CN 逐字节一致、dfg 通路用 add2 验证）→
  `rule_map.schedule`（SIMD 调度）+ `bank_alloc`（区间图着色分配器，淘汰 6 上限）+
  `cc.py` 的 `fold_addresses`/`route_links`（地址折叠 / 多跳 link 路由纯函数）。
  这套是为我们的 SIMD 执行模型量身写的，已通过 `stress_20leaf`（20 叶子 40cyc/640w
  自检 0 差异）、BN/CN 逐字节一致、全量回归 54/0 验收。
- **建议**：把 `docs/14`–`docs/16` 的"Morpher 当编译器"线标记为 **investigated-and-rejected**，
  精力回到 L1/L2 这套编译器 + 把更多真实 kernel（MMSE/FFT tile）铺上去。

### 10.4 对 docs/16 §7.2 的更正

`docs/16` §7.2 原写"写 16 条指令 + 8 寄存器 + acc 的 ADL → 映射成功 II=8 / 40 s"。
**更正**：该次映射实际跑的是原始 `hycube_original_mem.json`（带 `LOAD/STORE`+正确端口名），
不是描述我们硬件的 `gpcp_cgra_v2.json`。v2 对 mapper 的端口解析从不通，从未成功映射。
详见本 §10.2 (R1)。

## 11. 真实 kernel 接入：MMSE / FFT tile（本轮新增）

目标：证明 L1/L2 的 `kind: dfg` 通路不是只能跑 `add2`/`stress` 这类玩具图，而是能接
**真实基带 kernel 的 tile** 并生成可自检的微码。两个 tile 都是「一个 PE 一个实例、
16 个 PE 并行」的粒度——与阵列的 SIMD 广播模型一致。

### 11.1 两个 tile

| YAML | 真实含义 | 叶子 → 汇 | 规模 |
|---|---|---|---|
| `cgra/kernels/fft_butterfly.yaml` | radix-2 DIT FFT 蝶形（单蝶） | 6 输入（Ar/Ai/Br/Bi/Wr/Wi）→ 4 输出（A'/B' 的实虚部） | **32 拍 × 16 PE，512 字** |
| `cgra/kernels/mmse_2x1.yaml` | 2-Rx / 1-Tx MMSE 合并的**向量相关**：`num = conj(h1)y1 + conj(h2)y2`（Q30） | 8 输入（h1/h2/y1/y2 实虚部）→ 2 输出（numr/numi） | **32 拍 × 16 PE，512 字** |

FFT 蝶形：`t = W*B`（4 乘 2 加），`(W*B)>>15` 缩回 Q15，`A'=(A+t)>>1`、`B'=(A-t)>>1`。
MMSE 相关：`Re = h1r*y1r + h1i*y1i + h2r*y2r + h2i*y2i`，`Im = h1r*y1i - h1i*y1r + h2r*y2i - h2i*y2r`。

### 11.2 为了让真实 kernel 跑通，改了三处（通用能力，不是特判）

1. **`imm` 贯通 DFG（Q15 缩放必需）**：`DFG.node()` 新增 `imm`，`build_dfg` 透传
   `op.get("imm",0)`，`schedule` 对 `shr/shl` 用节点 imm（此前硬编码 `>>31`/`<<0`），
   `check_dfg` 黄金模型同步。`build_bn_dfg` 的 `H0` 补 `imm=31`（否则 `rule_map.py --bn`
   的硬判决会错——这是改动暴露的既有隐式约定）。
2. **声明序优先的拓扑排序（寄存器压力）**：`DFG.topo()` 由「按 level 排序」改为
   Kahn + 声明序小根堆。原实现先发完所有 level-1 乘积，MMSE 的 8 个乘积同时占满
   8 个 GPR → `寄存器不够`。改后 `c1` 子链完整发完再发 `c2`，`max_regs` 降到 5（FFT 为 6）。
3. **16×16 `mul` 的硬约束**：`simulate`/RTL 的 `mul` 是 `_s32(_sx16(x)*_sx16(y))`——
   **两操作数都按 16 位截断**。MMSE 若把 32 位 Q30 的 `numr` 再乘 `inv_denom` 会直接变垃圾
   （实测误差 40120 LSB）。因此 tile 边界定在**复数相关输出 Q30**，标量 `1/(|h|²+σ²)`
   归 CVA6（正好是 SoC 的标量/向量分工）；输入契约 `|leaf| ≤ 20000` 防 4 项 Q30 求和溢出。

**头文件新增 bank 映射**：dfg 产物除 `*_PROG_CYCLES/PES` 外，再导出
`<SYM>_BANK_<NAME>`（每个叶子/汇的 spad bank）与 `BANK_LO/HI`，供 C 基准按 bank 布局
组织 DMA；`mmse_2x1` 实测叶子 bank 0..7、汇 8..9。

**踩过的三个坑（都是"流程成功、数据错"，只有逐值对账能抓）**：

1. **32 拍阵列太短**：`rt_wait_array` 会读到上一轮遗留的 DONE 立即返回。必须

2. **`rt_dma_run` 误判**：start 被 busy 忽略时它仍返回成功。DMA 启动要显式
   "清 done → 等 busy 落 → 启动 → 轮询 done"。
3. **D-cache**：引擎/DMA 直接写 RAM 后，CPU 读同一行会命中旧值；`rt_dcache_flush()`
   是异步排空，紧跟其后的读仍可能命中旧行。最终改为**直接从 spad 主机窗口读汇**
   （MMIO 非缓存），彻底绕开。

### 12.2 为此新增的编译器能力（都是通用能力）

1. **flat 地址 `addr: {base, stride}`**：spad 平坦下标 = `base + stride*instance`。
   - `stride: 16`：每个 PE 往后挪 16 字（PRACH 的 y/ref 窗口，t=8p+k）；
   - `stride: 0`：所有 PE 共享同一字（FIR 抽头 / 广播系数）；
   - `stride: 2` + 原地汇：交错双字（PRACH 部分和 512+2p）。
   带 addr 的叶子/汇不参与 bank 分配，`imm` 直接用 10 位平坦地址（0..1023）。
2. **`neg` 伪算子**：降为 `sub a=zero b=x`（Polar 的 `-beta` 需要）。
3. **`sinks` 名字校验**：`sinks:` 里的名字必须真的是「无后继算子」，否则报错
   （开发中曾把 `part_r/part_i` 写成最后一级之外的名字，汇被静默分到 bank 0/1）。
4. **自检按 spad 地址初始化**：`stride=0` 的广播叶子、地址重叠的叶子共享同一个随机值，
   与硬件「预装一次」的语义一致（旧模型按「叶子×实例」初始化，广播叶子会互相覆盖）。

### 13.2 sss：三个布局都得重新映射

sss 的手写微码假设的 spad 打包，是照着 **DMA 描述符的 row/stride** 长出来的：

| 区域 | 手写版 spad 形状 | 平坦下标 (PE p, tap k) | 能否线性表达 |
|---|---|---|---|
| x (I/Q) | `row=0` 连续 254 字 | `2t = 16p + 2k` | ✅ `base 2k, stride 16` |
| ref | `row=16`（每 bank 16 字） | `256 + 32·⌊t/16⌋ + (t mod 16)` | ❌ 步长在 8/24 之间交替 |
| 汇 | `row=2, stride=32`（16 个 bank） | `512 + 32p`、`513 + 32p` | ✅ 但占满 16 bank |

ref 这一条形如 `256 + 8p + k − 8·(p mod 2)`：每 16 个 tap 换一次 bank，PE 的窗口跨在
bank 边界上，`base + stride·instance` 表达不了。两个可选修法：

1. 给编译器加「分块地址」模式（`base, stride, block, block_stride`）——为一个 kernel 加一种寻址；
2. **改 DMA 的打包形状**，让 ref 变成每 PE 一块（`row=8`），地址自然线性。

选 2。这不是绕过问题，而是把「spad 怎么摆」明确成编排层的自由：ref 只是一张表。
改完后 `ref = 256 + 32p + k`（`base 256+k, stride 32`）。

代价是 **bank 预算**：imm 只有 10 位，一页只有 32 个 bank（1024 字）。

```
x 8 bank + ref 16 bank（每行 8 字）+ 汇 16 bank = 40 bank > 32   ← 装不下
```

所以汇必须压缩：`part_r/part_i` 按 PE 相邻放（`768+2p`、`769+2p`），只占 **1 个 bank**，
DMA 用 `row=0` 连续搬 32 字回 RAM，RAM 里的顺序仍是 `{re0,im0,re1,im1,…}`，与
`metric_of()` 的读法完全一致，检查器一个字都不用改。

```
x 8 bank + ref 16 bank + 汇 1 bank = 25 bank ✓
```

> **教训**：编译器只负责「指令流」，spad 形状由 DMA 描述符（`len / stride / row`）决定。
> 让 kernel 可编译的最有效手段往往不是加寻址模式，而是把 spad 重新打包成线性——
> `row` 就是那个旋钮。

拍数 52 → 66：编译器没有 `MAC/acc`，实部只能 `mul + add` 两条链（手写用 `MAC` 一条）。
sss 门禁总周期 221589，其中阵列部分 337 × 14 ≈ 4.7k（约 2%）；真要抹平得给编译器加
累加器支持，见 §13.5。

### 13.3 已换的两个 bench 各自的验收点

- **polar**：`check_sc.py` 是独立黄金模型（同 frozen 规则、同 LCG、min-sum f/g），
  64/64 位逐位 + 32 信息位全恢复，说明节点微码的符号/取反/移位都对。
- **sss**：`check_sss.py` 比对 **检出候选与真候选两组 16 路部分和**（32 值 ×2）逐位，
  比只看「检出对不对」强得多——部分和错但排序侥幸对的情况会被抓住。

### 13.4 rxchain 为什么不换：融合是编排层的事

`rxchain_bm.c` 的一个 slot 跑的是**一张 127 拍的融合镜像**，四个阶段共用同一批 bank
的**不同 word**（`Yr,Yi,Xr,Xi` → `Hr,Hi` → `Nr,Ni,|H|²` → `min1,min2,sign`）：

```
槽位   手写   编译器单独编这个 kernel
A chrest  15   18  (chnest16)
B MMSE    20   32  (mmse_2x1)
C 解映射  40   —   （没有 YAML；16-QAM max-log）
D CN      52   172 (pdsch_cn，粒度不同：那边是整节点，这里是 4 消息)
```

三点结论：

1. **槽位比编译器紧**。手写 chrest 是 14 条指令塞进 15 拍（每拍一条，贴着发射上限）；
   编译器给 18 拍，因为它**每个消费者都现场 `LD` 一次叶子**（`Yr/Yi/Xr/Xi` 各被用两次，
   于是多 4 条 `LD`）。这是调度器的已知优化项，不是错误。
2. **槽内是 spad 复用**，不是数据流。编译器的 DFG 只有「入口叶子 → 算子 → 出口汇」，
   没有「中途写 spad 再读回」。要表达融合镜像，得把 4 个 kernel 的中间值全部留在寄存器里，
   8 个 GPR 根本不够。
3. **CN 槽是另一个 kernel**（4 消息节点），和 `pdsch_cn_prog.h` 的整节点不是同一粒度；
   硬套 172 拍会把这一个 slot 的阵列时间拉到原来 2 倍以上。

所以 rxchain 保留手写融合镜像，并在本文档固化这条边界：**「一个 kernel 一张微码」由
编译器负责，「多 kernel 融合成一张镜像、镜像内用 spad 当 scratch」是编排层的活**。
真要做，正确路径是给编译器加「分段 + scratch 分配」（多段 DFG、段间按 bank 传值），
而不是硬把单 kernel 调度器拉长。

### 13.5 编译器剩下的两个已知优化项（都是量化过的）

| 优化项 | 现状 | 收益 | 影响面 |
|---|---|---|---|
| **叶子驻留寄存器** | 每个消费者现场 `LD` | chrest 18 → 14 拍（贴上手写）；其余 dfg kernel 普遍省 2–4 拍 | 需要新的寄存器压力策略，20 个 kernel 的输出会变（bank/拍数），得全量重验 |
| **`MAC/acc`** | 未支持（`simulate` 直接报错） | sss 66 → ~52；点积类（FIR/PRACH/chrest）省一半算术指令 | 要给 `acc` 建生命周期（一个 PE 只有一个累加器），并让模型/自检支持 |

两项都不影响协议功能，属于「把编译器产物压到手写密度」的后续工作。

## 14. Zc=64 的边消息分页 + 分层调度落硬件（BG2）

`AGENTS.md` 里最后一条协议缺口是「BG1 / Z=64（边消息分页、层调度）」，模型侧
`tools/nr_ldpc.py` 早就自检通过，硬件侧一直没做。本节把其中**不依赖 BG1 官方表**的那
一半做掉：BG2 在 **Zc=64** 上做边消息分页 + 分层（layered）min-sum，新门禁
`run-pdsch-zc64`。

### 14.1 为什么 64 需要分页，而 20 不需要

一个 PE 一次只持有一个提升值（`word = 提升行`），所以一条 64 长的边消息必须拆成
**4 页 × 16 值**：

```
检查节点 r 的第 k 条边、第 j 页  ->  spad bank k, word 0..15   (j = 0..3)
```

CN 微码**完全复用** Zc=20 那张 172 拍程序的前半（86 拍：PE p 负责提升值 p，10 条边在
bank 0..9，min1/min2/sign 回 bank 10..12）。变的只是编排：每个「(检查节点, 页)」是一次
DMA + 一次 86 拍运行，一共 42 × 4 = 168 次。

```
per (r, j):
  CPU  gather v2c = total[col][(16j+i+sh) % 64] - c2v        -> stage[10][16]
  DMA  stage -> bank 0..9 word 0..15            (row=16, stride=32, len=160)
  array 86 拍（page = (r*4+j)&1，双页轮换）
  CPU  读回 bank 10/11/12 word 0..15（spad 主机窗口，非缓存）
  CPU  total[col][idx] += c2v_new - c2v_old ；c2v = c2v_new     ← 分层就地更新
```

`total += new - old` 在**同一层**算完就做，所以下一层看到的是已经含本层更新的总消息——
这正是 layered 相对 flooding 的收敛优势，`tools/nr_ldpc.py` 的 `layered_decode` 就是
这个口径。

### 14.2 三个只有逐值对账才能抓到的坑

1. **argmin 判定要用 CN 输入，不是上一条消息。**
   用 `min1/min2` 还原「除自己外的最小值」时，判据是 `|v2c_k| == min1`。第一版写成
   `|c2v_old| == min1`：首轮 `c2v_old` 全是 0、而 `min1` 也是 0（有打孔列），于是**每条边
   都被判成最小值而取 min2**，一个节点内所有边拿到同一幅度。
   致命的是：**syndrome 仍然是 0、硬判决仍然全对**（符号没坏），只有 `total` 绝对值错。
   这类 bug 只能靠 value-by-value 对账抓——和 §12.3 的 PRACH 是同一类教训。

2. **检查器不能拿信道 LLR 当期望。**
   分层译码里第 r 行的 CN 输入**已经包含前 r 行的更新**，只有第 0 行等于信道值。第一版
   检查器直接对 `chan` 求 min-sum，结果第 0/1 行「通过」（那两行的 c2v 恰好是 0）、第 2
   行起全错——差点误判成硬件错。正确做法是让检查器**重放一遍分层过程**，把每行的 CN
   输入也一起产出（`layered_model()` 返回 `cn[(row,page)]`）。

3. **两处内存一致性，方向相反。**
   - CPU 写 `stage` → 拷贝引擎读 RAM：D-cache 是写通，但 **store buffer 不是**，必须先
     `fence iorw` 并回读一个字排空（和 `build_ref_table` 里的写法一致）。
   - 引擎写 spad → CPU 读：走 **spad 主机窗口（MMIO，非缓存）**，不要 DMA-out + D$ 失效
     （§11.5 踩过：失效是异步排空，紧跟的读仍可能命中旧行）。

### 14.3 结果

```
[ OK ] Zc=64 BG2 block, edge messages paged 4 x 16: min1/min2/sign bit-exact on
       every page, 4 layered iteration(s) matches the model value for value,
       zero syndrome, 384/384 information bits
[info] zc 64, 42 check nodes x 4 pages, 672 array runs, 672 DMA, 4064839 cycles
```

| 迭代 | 阵列运行 | 周期 | 结果 |
|---|---|---|---|
| 1 | 168 | 1.01 M | 逐值一致（但见下面的收敛表：1 次还不够） |
| 2 | 336 | 2.03 M | 逐值一致 |
| 4（门禁默认） | 672 | 4.06 M | 逐值一致、syndrome 0、384/384 信息位 |

门禁默认工作点 σ=5（`--sigma`，即未打孔比特上的加性噪声），因为 **σ=0.5 的默认激励
过于干净**：任何 SNR 都一次迭代收敛，测不出「分层」的意义。σ=5 时模型侧：

```
it1: 725 syndrome bits | it2: 203 | it4: 0 | it8: 0     (σ=6 时 8 次才 0)
```

所以门禁的四次迭代是**真的在迭代**，不是一次就收敛的假象。`SIGMA=` / `ITERS=` / `SNR=`
可换点。

### 14.4 边界：BG1 仍然缺官方表

这次做的是 **BG2 在 Zc=64** 的分页 + 层调度，与 `tools/nr_ldpc.py` 逐值对齐。
**BG1 仍未做**，原因不是缺编排能力，而是仓里没有 38.212 Table 5.3.2-2 的官方移位系数
（`tools/ldpc5g.py` 只内置了 BG2 的 `BG2_A5`）；按 `nr_ldpc.py` 的注释，接 BG1 只需要
把 `BG2_A5` 换成 BG1 的基矩阵加 `ROWS/COLS/KB`，分页/层调度的代码可以原样复用
（Zc=64 已经是 4 页，BG1 的 Zc 集合同样按 16 整除）。所以这条缺口的性质是**数据缺**，
不是能力缺。
