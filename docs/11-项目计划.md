# GPCP 项目计划（以协议过程为阶段）

> **本文件取代已删除的 `docs/03-路线图.md`**，是项目唯一的计划与验收依据。历史里程碑（M0–M2.5、B3 冻结）保留在 §7，不再单独维护。

## 0. 制定原则与验收框架

1. **阶段 = 一个可端到端跑通的 3GPP 协议过程**，而不是一个硬件模块或一项性能指标。
   「做完一个信道」不算完成；「该过程的消息/字段齐备、能被接收端解出并闭环」才算完成。
2. 本项目是 **「双向接收引擎 + 黄金模型发射端」** 的链路级原型：
   - SoC 侧实现**接收**：下行时扮 UE（SSB/PDCCH/PDSCH），上行时扮 gNB（PRACH/PUCCH/PUSCH）；
   - 发射侧由 Python 黄金模型产生波形/消息。
   - 因此每阶段验收 = **发射端模型 + 接收端硬件/模型，把该过程的消息正确解出并闭环**。
3. 沿用仓库铁律：每个里程碑必须有**可运行的仿真 + 可自动比对的黄金模型**，检查器不许空转。
4. **支撑线**（实时性、8×8、Linux、PPA）不单独成阶段，按依赖挂到对应协议阶段之前。

## 1. 终态定义（三档，避免「完整」含糊）

| 档位 | 定义 | 当前粗估 |
|---|---|---|
| **L1 完整** | 下行 SSB/PDCCH/PDSCH + 上行 PRACH/PUCCH/PUSCH **全部上硬件**，DCI 驱动、HARQ、满足 slot 预算 | ~80% |
| **协议完整** | + 最小 L2（MAC/RLC/RRC）+ 调度器 + 端到端（QEMU/free5GC ping/iperf） | ~30% |
| **平台完整** | + Linux 用户态 + 8×8 阵列 + PPA/FPGA | ~35% |

## 4. 阶段划分

### P1 — 小区搜索与系统信息（让 UE「能驻留小区」）✅ 已交付
- **协议范围**：SSB/PBCH/MIB（已完成）+ **SIB1**：CORESET#0、公共搜索空间（CSS）、SI-RNTI 加扰的 PDCCH、承载 SIB1 的 PDSCH、SI 窗调度。
- **消息/信道清单**：PSS/SSS/PBCH/MIB（已有）；CORESET#0 配置；DCI 1_0（SI-RNTI）；PDSCH（SIB1，含 RRC `SIB1` ASN.1 容器）；SI 窗/周期。
- **交付物**：`tools/nr_sib1.py`（SIB1 ASN.1 + 调度）；SIB1 的 PDCCH/PDSCH TD 生成；复用 `run-pdcch`/`run-pdsch-full` 接收；新增 `run-sib1`；`verify.sh full` 纳入。
- **验收（过程级）**：从 TD 样本解出 **MIB + SIB1**（小区 ID、SFN、PRACH 配置、CORESET#0、SI 窗），逐字段与黄金模型对账；`run-sib1` `[OK]`。
- **当前差距**：SIB1 的 RRC ASN.1、CORESET#0/CSS 配置（当前 PDCCH 为简化盲检）。
- **依赖**：无（SSB/PDCCH/PDSCH 已具备）。
- **状态（2026-11-05）**：✅ 已交付 `tools/nr_sib1.py` + `run-sib1`。SI-RNTI 0xFFFF 单候选；rv=0/2 均 `[OK]`（k0=0/492），0 errors、4.43 M 周期、2208 次阵列运行；SIB1 字段（cell_identity/tac/prach_config_index/msg1_fdm/msg1_freq_start/zero_corr_zone/scs）与配置逐值一致；`verify.sh full` 已纳入 `model-sib1` / `run-sib1`。

### P2 — 随机接入（让 UE「能接入」）
- **协议范围**：PRACH 前导（ZC，38.211 6.3.3）、PRACH occasion、RA-RNTI、**RAR**（MAC CE：TA/TC-RNTI/UL grant）、**Msg3**（PUSCH 承载 CCCH SDU）、**Msg4**（PDCCH/PDSCH 竞争解决）、TA。
- **消息/信道清单**：PRACH preamble；RA-RNTI 的 DCI 1_0 + PDSCH（RAR MAC CE）；Msg3 的 PUSCH（CCCH SDU）；Msg4 的 PDCCH/PDSCH（UE Contention Resolution Identity MAC CE）；TA command。
- **交付物**：PRACH 检测落硬件（`run-prach`：ZC 相关 + 定时估计）；`tools/nr_rach.py`（4-step 状态机）；RAR/Msg3/Msg4 复用现有 PDCCH/PDSCH/PUSCH 引擎；`run-rach` 过程级基准。
- **验收（过程级）**：**4-step RACH 全程跑通**——前导检出并给出正确 TA → RAR 解出（TA/TC-RNTI/UL grant）→ Msg3 发/收 → Msg4 匹配 → TC-RNTI 升级为 C-RNTI；`run-rach` `[OK]`。
- **当前差距**：无（PRACH 硬件、RA-RNTI、RAR/Msg3/Msg4、竞争解决已全部落地）。
- **状态（2026-11-05）**：✅ 三阶段一次交付完。**A** `tools/nr_rach.py`（4-step 过程模型：ZC 相关 8 点、RA-RNTI、RAR/CCCH/CR-ID MAC CE、3 次接入均一次 Msg4 解决，三类注入错误各自让对应门如实失败）。**B** `run-prach` + 第 15 个 kernel `prach_corr`（128 拍，`tools/gen_prach_prog.py` 生成）：**139/139 shift 与整数模型逐位一致**，峰 d=39 → preamble 2 / TA 9、16.6 dB 裕度、0 errors、139 次阵列运行 / 279 次 DMA / 4448 个部分和-归约交叉校验。**C** `run-rach`（`sw/soc/rach_bm.c`）：Msg1 → SoC 自算 RA-RNTI → Msg2 RAR → Msg3 PUSCH（FFT 窗口 = Msg1 实测 TA、用解码出的 TC-RNTI 解扰）→ Msg4 竞争解决 → C-RNTI，**一次 SoC 运行**；默认点 0 errors、**11,826,693 周期 / 5531 次阵列运行 / 4947 次 DMA**，三条腿各 1040/1040 硬判决 + CRC24A + TB 全对；第二点 **`MSG4_RV=2` 亦 `[OK]`**（硬件解出 rv=2 → k0=492），`OCC=` 换 occasion ⇒ 换 RA-RNTI。`verify.sh full` 已纳入 `model-rach` / `run-prach` / `run-rach`（2026-11-05：39 passed / 0 failed / 2704 s）。
- **刻意保留的简化**：RRC 用**紧凑定长位域**而非 38.331 ASN.1 PER（与 SIB1 同一口径，PER 留给 P3）；单 TTI/单频点、无 Backoff/重传、无 2-step、无 Msg3 变换预编码（DFT-s-OFDM）、无 PUCCH；RAR 的 27-bit UL grant 按 38.321 Table 6.2.3-2 的**紧凑字段集**解析（`fh/rb_start/rb_len/tda/mcs/harq_timing/tpc/power_class/rsv`）。
- **依赖**：P1（SIB1 提供 PRACH 配置）。

### P3 — RRC 连接与控制面（让 UE「能建立连接」）✅ 已交付
- **协议范围**：RRCSetupRequest/Setup/Complete（SRB0→SRB1）、RRCReconfiguration；MAC **SR/BSR/PHR**；PUCCH（SR）；TA 维护。
- **消息/信道清单**：RRCSetupRequest（CCCH）、RRCSetup（DCCH）、RRCSetupComplete；SR（PUCCH）、BSR MAC CE、PHR MAC CE、TA Command CE、C-RNTI CE。

- **验收（过程级）**：RRC 连接建立；SR 触发 UL grant；BSR 正确上报缓冲；TA 维持；`run-pucch` `[OK]`。
- **当前差距**：38.331 ASN.1 PER 编码（留给 P6）、CSI 上报、RRC 定时器、RLC 分段/PDCP 加密。
- **依赖**：P2（C-RNTI）。
- **状态（2026-11-05）**：✅ 三阶段一次交付完。**A** `nr_rrc.py` 5 类消息 SDU/PDU/TB 逐层往返 + 4 类 MAC CE 往返 + 状态机 `IDLE→SRB1_CONFIGURED→CONNECTED→CONNECTED_RECONFIGURED`（TA 9→11），错 C-RNTI 被拒；`nr_conn.py` 全过程跑真实 PHY，**5 类注入错误**（错 C-RNTI / 无 SR / 错 BSR / 错 TA CE / 跳过 SRB1）各自让对应门如实失败，DFT-s-OFDM 上行与 seed 2/3 亦 `[OK]`。**B** `nr_pucch.py` 整数黄金模型：4 个 SNR × 16 点全对且与 `nr_ul.py` 浮点模型 100% 一致。**C** `run-pucch`（`sw/soc/pucch_bm.c`）复用 `prach_corr` 微码只跑 2 个候选 m_CS=0/6：ACK=1（25.9 dB）/ ACK=0（24.7 dB）/ 0 dB seed 3（14.7 dB）三点 `[OK]`，0 errors、2 次阵列、5 次 DMA、64 个 PE 分部逐位对账。`verify.sh full` 已纳入 `model-rrc` / `model-conn` / `model-pucch` / `run-pucch`（全量回归待复验）。

## 5. 支撑线（并行，不单独成阶段）

| 支撑项 | 现状 | 挂载点 |
|---|---|---|
| **20 ms slot 预算** | 单 SSB 4.34 M 周期 @100 MHz ≈ 43 ms，超 2.2× | **P4/P5 前**（否则「实时」不成立） |

## 6. 依赖关系与关键路径

```
P1 小区搜索/SIB1
   │
   ▼
P2 随机接入（PRACH/RAR/Msg3/Msg4）
   │
   ▼
P3 RRC 连接 + 控制面（SR/BSR/PUCCH）
   │
   ├──────────────┐
   ▼              ▼
P4 下行数据面   P5 上行数据面
   │              │
   └──────┬───────┘
          ▼
P6 L2 用户面（SDAP/PDCP/RLC/MAC）
          │
          ▼
P7 核心网/端到端（NGAP/N3/GTP-U/free5GC）
          │
          ▼
P8 移动性/寻呼/SI 更新（可选）
```

- **关键路径**：P1 → P2 → P3 →（P4 ∥ P5）→ P6 → P7 → P8。
- **可与协议线并行**：P4/P5 的硬件精化（BG1/Zc64、MIMO、TP、功控）、20 ms、8×8、Linux；它们不阻塞 P2/P3 的协议过程闭环，但在 P4/P5 验收前必须收口。

## 9. 风险与决策点

| 风险/决策 | 影响 | 建议 |
|---|---|---|
| 20 ms 预算（43 ms，2.2×） | L1 不实时 | 优先 FFT 尾块 128→512 合并 + DMA 摊销 + 提频；或明确「非实时原型」定位 |
| spad 16R/16W（~2.6 mm²） | 8×8 面积爆炸 | 先重排 kernel 数据布局再 bank 化（`docs/08` §3.2） |
| Linux 冻结 | 平台完整度 | 时间盒解冻（内置 initramfs，约 20 min 编译 + 40 min 仿真） |
| L2 工作量最大 | 进度风险 | 先 MAC + RLC UM 最小闭环，RLC AM/PDCP/RRC 后置 |
| RACH 4-step vs 2-step | P2 范围 | 第一版按 4-step（覆盖 RAR/Msg3/Msg4，教学与验收更完整） |
| 20 ms 是否硬指标 | P4/P5 排期 | 需拍板 |
