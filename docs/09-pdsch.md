# 09 — PDSCH（SISO）：P2 里程碑第一步（模型级）

> 目标：从"只解广播信道（SSB/MIB）"推进到"能传数据"。这一步先把**下行共享信道的完整
> 数学模型**立起来并且跑通，作为后续 CGRA 微码/裸机 benchmark 的黄金模型。
> 硬件（CGRA kernel + `run-pdsch`）是下一步，不在本文范围内。

## 1. 链路与参数

```
TB(80 bit) → CRC24A → 38.212 LDPC(BG2, Kb=6, Zc=20, N=1040)
           → 速率匹配（圆形缓冲比特选择，跳过 filler）→ 加扰（Gold, c_init=n_RNTI·2^15）
           → QPSK → RE 映射（2 符号 × 240 RE，每 4 个 RE 一个导频）
           → 信道（平坦增益 + AWGN / 两径频选）→ 每符号导频 LS 估计 → 均衡
           → QPSK 软解调 → 解扰 → 解速率匹配（重复位 LLR 累加）
           → min-sum LDPC 译码 → CRC24A 校验 → TB 比对
```

| 参数 | 值 | 说明 |
|---|---|---|
| TB 长度 A | 80 bit | 小包，便于逐位核对 |
| K = A + CRC24A | 104 bit | 38.212 §7.1，多项式 `0x864CFB` |
| 基图 | **BG2**（38.212 Table 5.3.2-3） | Kb=6（CBS ≤ 560），Zc=20（i_LS=2，a=5） |
| 编码块 N | 52×20 = **1040 bit** | 前 2·Zc = 40 bit 打孔，不传输 |
| filler | 16 bit | `Kb·Zc − K`，速率匹配时跳过、译码时置 0 |
| 传输比特 E | **720 bit**（QPSK 360 符号） | 2 符号 × 180 个数据 RE |
| 等效码率 | ≈ 104/984 ≈ **0.11** | 很低，所以门限很低（见 §3） |

## 2. 实现要点

1. **BG2 移位表**：`tools/ldpc5g.py` 内嵌 42×52 的移位系数（-1 = 零块），来自 3GPP RAN1
   文稿 **R1-1711982**（"Base graph design"，即 38.212 最终表），取 **i_LS = 2（a=5）**，
   可用 Zc ∈ {5,10,20,40,80,160,320}。
2. **编码不用高斯消元**：直接用 BG2 的双对角结构——
   `p10` 由前 4 行求和后以 shift-1 反解，`p11/p12/p13` 顺序回代，其余 38 行都是
   `p_{r+10} = 该行其余项之和`。`syndrome(c) == 0` 是自检（本仓库实测 0）。
3. **min-sum 译码**：flooding、归一化因子 0.75、20 次迭代；打孔位按"已知 0"处理
   （`llr=0`），填充位（filler）在解速率匹配时置 0。
4. **速率匹配**：圆形缓冲 = `cw[2·Zc:]`（跳过 filler），`rv=0`，E=720 < 984 所以无重复；
   解匹配时按同一索引累加（重复会自然合并 LLR，为后续 HARQ 留接口）。
5. **导频（step 1 简化）**：每 4 个 RE 一个恒定的 `+QPSK` 导频，接收端已知其值，
   因此这一版只验证**数据通路**；真实 DMRS（Gold 序列 + 38.211 `c_init`）沿用 SSB 链里
   已验证的那套，留到硬件步骤一起换。

**尚未实现（下一步清单）**：38.212 §5.4.2.2 比特交织、HARQ 软合并与 RV、PDCCH/DCI 与
MCS 表、层映射/预编码（SISO）、解速率匹配/LLR 的微码、以及 `run-pdsch` 基准。

**已经落到 CGRA 上的部分**（step 2a，`make -C sim/soc run-pdsch`）：

| kernel | 拍数 | 内容 |
|---|---|---|
| `ldpc_cn`（已有） | 52 | 4 入 min-sum 检查节点：`min1`/`min2`/符号积 |
| `ldpc_bn`（新增） | 19 | 变量节点：`v = ch + Σm`，`m' = v − m`，并输出硬判决（−1 = 1） |

一个 kernel 覆盖 **16 个提升后的节点**（Zc/16 次运行覆盖一个编码块），两者都已进入
`python3 tools/cgra.py test` 的逐位回归（14/14，`ALL TESTS PASSED`）。

**迭代闭环基准**（`sw/soc/pdsch_bm.c` + `tools/check_pdsch.py`）：8 个变量节点 / 4 个检查节点
的小图，每次迭代 = 一次检查节点运行（50 拍）+ 一次变量节点运行（12 拍），CPU 负责在两级之间
搬 16 条边消息并做 per-edge 重构。8 次迭代 = **16 次阵列运行、50,721 周期**；输出
`[-1,-1,-1,-1,-1,-1,0,0]` 与 Python 黄金模型逐位一致，且其中 **2 个判决确实被迭代翻转**
（相对原始信道符号），所以这条验收不是"硬判决恒等"的空转。

**真实 BG2 块的 DMA 分块**（step 2b，`make -C sim/soc run-pdsch-bg2`）：

一个 BG2 编码块需要 52·Zc 个 LLR + 197·Zc 条消息（Zc=20 约 5000 词），远超 8 KiB scratchpad
（单页 1024 词），所以译码必须**按检查节点分块**。`sw/soc/pdsch_bg2_bm.c` 的做法：

| 步骤 | 说明 |
|---|---|
| 数据驻留 | RAM 中的 `llr[52][20]`、`msg[42][10][20]`（每条边的消息） |
| 搬入 | 2D DMA（`row=20, stride=32`）把某个检查节点的 10 个 bank 一次送进 spad：bank k = 边 k、word i = 提升行 i；不足 10 条边的用 **+32767 哨兵**补齐 |
| 计算 | 两个阵列运行覆盖 20 个提升行（PE 0..15 做 0..15，PE 0..3 做 16..19）：10 输入 min-sum，哨兵保证不影响 min1/min2、符号为 0 |
| 搬出 | 3×20 词（bank 10/11/12 = min1/min2/sign）DMA 回 RAM |

实测 **42 个检查节点 × 20 提升行全部逐位一致**：84 次阵列运行、84 次 DMA、**631,360 周期**。
哨兵 padding 让同一份 10 输入微码覆盖所有度数（BG2 的检查节点度数是 3…10），
不需要为每个度数单独生成程序。

> 还没做的：BN 更新与多次迭代（本轮只验证了"真实块 + DMA 分块 + 全图 CN"这条管线）；
> 下一步把它接上 BN（可在 CPU 侧做，或再加一个流式 BN 微码），跑完整迭代并检查 CRC。

## 4. 与 SSB 链的关系

| | SSB（已验收） | PDSCH（本文） |
|---|---|---|
| 波形 | 时域样本 → 4096 点 FFT | 直接给频域 RE（FFT 已单独验收） |
| 信道估计 | 28 导频/符号，单复增益 | 60 导频/符号，单复增益（同口径） |
| 编码 | Polar（38.212，SC 译码） | LDPC（BG2，min-sum 译码） |
| 加扰 | `c_init = 3·N_ID1+N_ID2` | `c_init = n_RNTI·2^15` |
| 输出 | MIB 32 bit | TB 80 bit + CRC24A |

两条链共用同一套"频域网格 → 导频 LS → 均衡 → 软解调 → 译码 → CRC"骨架，所以下一步
把导频换成真实 DMRS、把均衡换成 MMSE、把译码搬上 CGRA，都是**增量改动**。

### 4.1 进行中：流式 BN 与完整迭代（本轮未通过，已回退）

按"CN 分块"的同一套路实现了变量节点的流式版本：

- **BN 微码**：24 个消息槽（0 填充）+ 1 个 LLR（bank 24）+ 1 个硬判决（bank 25），
  `v = llr + Σ m`、`m' = v − m`、`hard = sign(v)`，约 125 拍；`dump` 出来的 16 位/20 行用
  两次阵列运行覆盖（Zc=20 > 16 PE）。
- **调度**：每次迭代 = 42 个检查节点（已有，631k 周期）+ 52 个变量块（gather → DMA 进 →
  2 次运行 → DMA 出 → scatter），8 次迭代共 1504 次阵列运行、约 18.4M 周期。

**结果：不一致。** 8 次迭代后 1040 个硬判决里约 28% 与 Python 模型不同（1 次迭代时相同比例）。
已排除的部分：CN 的 `min1/min2/sign` 与模型**逐位一致**（`run-pdsch-bg2`），
所以问题落在"提升移位（lift shift）在校验坐标 ↔ 变量坐标的转换，以及块内原地回写"
这一层——目前 gather/scatter 用的是 `j = (i − sh) mod Zc`，仍与模型对不上。

按"只跑 1 个变量块"的办法做了隔离实验（`sw/soc/pdsch_bn1_bm.c` +
`tools/check_pdsch_bn1.py`，`make -C sim/soc run-pdsch-bn1`）：

- 24 个消息槽 + LLR（bank 24）+ 硬判决（bank 25）共 **520 个值**，随意输入下
  硬件输出**逐值**等于黄金模型（`v = llr + Σm`、`m' = v − m`、`hard = sign(v)`），
  2 次阵列运行、2 次 DMA、0 错误。

**结论：BN 微码本身正确，问题在整条调度里**——即"变量块按提升移位 gather/scatter 到
`msg[r][k][·]`"这一步，或 CPU 侧逐边重构的循环。这个隔离基准保留在仓库里（`run-pdsch-bn1`），
下一轮把 gather 后的 24 槽输入再和模型比一次即可定位。

进一步按"验证 gather 后的 24 槽输入"做了一次隔离（`sw/soc/pdsch_gather_bm.c` +
`tools/check_pdsch_gather.py`，`make -C sim/soc run-pdsch-gather`）：

- **逐边重构完全正确**：22 条边的 22×20 个重构消息与模型逐值一致；
- **gather 正确**，但前提是先把提升移位对 Zc 取模：`j = (i − (V % Zc)) mod Zc`。
  直接用表里的 V（最大 175）做 `i + Zc − V` 会**无符号下溢**，20 个值全错——这就是
  完整迭代里 28% 不一致的主要原因（只有 V > Zc 的边出错）。

修好后的完整迭代基准仍然不通过（约 50% 硬判决不同），已再次回退；剩余待查点集中在
BN 回写/散布（scatter 的逆映射与 `emit` 目标数组都改过，但未收敛）。本轮的**已修bug**
（V % Zc、`emit` 目标数组）与隔离基准都保留在仓库里，`run-pdsch-gather` 进入回归。

### 4.2 BN 输出有了结论：0 差异（并找到"28% 不一致"的真凶）

按"独立缓冲 + 有符号比较"重做了 `run-pdsch-gather`：

- BN 的输入、输出**各用一块缓冲**（不再原地回写）；
- 判据全程按**有符号 32 位**比较，并额外把 DMA 进来后的 **spad 内容**也 dump 出来对照
  （`spad == RAM`，0 差异 → 搬运链路无问题）；
- 结果：**输入一致性 0 差异、BN 输出 0 差异、硬判决全对**（22 条边 × 20 提升行）。

**真凶**：`emit()` 把**指针实参**当作数组下标（`prog_half[which]`），于是 BN 程序从来没被
写入 IMEM（阵列跑的是 NOP），输出等于输入。修法是把 `emit()` 改成接收目标数组
（`emit(uint32_t *p, ...)`）。这个 bug 之前只在完整迭代基准里修过，重建时又从旧文件复制，
所以又复发了——这次连"spad dump 对照"一起固化进判据，避免同类问题再漏。

至此真实 BG2 块的四段（CN → 逐边重构 → gather → BN → 硬判决）都已在硬件上逐值对齐。

### 4.3 串成完整迭代：仍然不一致（本轮）

把这四段按 8 次迭代串起来（1504 次阵列运行、约 20.5M 周期），结果 1040 个硬判决里
**552 个**与模型不同；只跑 **1 次迭代**也是 **503 个**——而且**每个变量块都错**（每块 1~14 位），
包括单块基准里完全正确的块 0（差 1 位）。

也就是说：**单块路径逐值正确，但一放进"52 个块串行"的循环里就出错**。差异必然来自块间
的串行状态，候选：

1. `gath` / `bout` 两块缓冲在块间复用（`n` 行以外的槽清零、第 25 行硬判决是上一块的残留）；
2. CN 结果缓冲 `res` 在所有块 scatter 完之前就被下一轮覆盖；
3. 循环里 `n` 的复用与 scatter 的逆映射（`msg[i] = bout[(i + sh) % Zc]`）。

按此做了隔离实验（`pdsch_loop1_bm.c`：只跑 1 次迭代，52 个块串行，**在循环内部** dump 块 0）：

- **块 0 在循环内输入 0 差异、BN 输出 0 差异、硬判决 0 差异** —— 与单块基准完全一致；
- 但其余块（1..51）的硬判决仍差 **492/1020**。

所以问题不在"块 0 的数据/复用"，而在**块与块之间**：块 0 的 scatter 或某个跨块状态影响了
后续块的 gather。新发现的候选：scatter 的逆映射只写了本块自己的 `(r,k)`，但 `gath` 的第 25 行
（硬判决）在块间残留、以及 BN 的输入行 `n..23` 清零位置是否随 `n` 变化 —— 需要把块 1 的
BN 输入也 dump 出来对照（下一轮）。

（调试过程中还发现：把 dump 放在结果区 500/1020 会与"52×20 硬判决区"（8..1047）重叠，
已改为 1100/1620 —— 这个坑同样记在案。）该基准已回退，仓库保持绿色。

补充数据点（同一轮）：把单块基准的 `TARGET` 改成 **1** 重跑 —— **重构 0 差异、gather 0 差异、
BN 输出 0 差异**。加上上一轮的"块 0 在循环内也全对"，可以确定 CN/BN 的算术本身没问题，
剩余差异只可能来自**循环里块与块之间的状态**（共享缓冲或调试 dump 的索引），
下一轮把**块 1 从循环内部** dump 出来对照即可定案。

**块 0 + 块 1 同时在循环内 dump（本轮结论）**：

| 块 | 边数 | 输入 vs 模型 | spad vs RAM | BN 输出 vs 模型 | 硬判决 |
|---|---|---|---|---|---|
| 0 | 22 | 0 差异 | — | 2 | 1 |
| 1 | 23 | 0 差异 | **0 差异** | **384** | 12 |

也就是说：**BN 的输入（RAM 与 spad 都核对过）与模型完全一致，但同一份微码在循环里跑出来的
BN 输出却与模型不同**，而在"单独跑"时同一块 1 是 0 差异。这排除了 DMA、gather、输入数据
和 BN 算术本身，剩下的只能是**块间残留的阵列/IMEM/页状态**（例如上一块 BN 写过的
bank 23/25 在下一块 DMA 只覆盖部分行、或 IMEM 载入与上一块运行的重叠）。

下一步建议：在块 1 的 BN 运行前后各 dump 一次 **spad 全部 26 bank**（现在只 dump 了运行前），
并检查 `load_prog_bn` 与上一块 `array_run_bn` 的完成/覆盖顺序。

**块 1 运行前后全 26 bank dump + IMEM 时序检查（本轮结论）**：

- 在 `array_run` / `array_run_bn` 里都加了"**先等 BUSY 置位、再等它清零**"（防止 posted
  store 让第一次轮询读到旧的 idle 状态而提前返回）——**结果没有变化**，所以不是这个时序问题；
- 循环内块 0 的 **BN 前 spad、BN 后 spad、硬判决全部 0 差异**（逐值）；
- 但块 1..51 的硬判决仍差 ~503/1020。

结合上一轮"块 1 的输入与 spad 完全正确"，现在可以确定：**同一份 BN 微码、同一份输入，
单独跑正确、循环里跑不正确**。剩下的嫌疑是**块间共享的 spad bank 内容**，特别是
`bank 13`：

- CN 微码把 `bank 13` 当作 **+32767 哨兵**（CPU 预装一次）；
- BN 微码的 24 个槽是 `bank 0..23`，其中 **bank 13 就是第 14 个消息槽** → 任何一块的 BN
  都会把它覆盖成 `v − m`；
- 本次只跑 1 次迭代，所以还不影响本轮 CN；但**8 次迭代时第二轮 CN 的哨兵就被破坏了**。
  对块 1..51 目前还解释不了"输入正确、输出错"，需要下一步在块 1 的 BN **前后**各 dump
  一次全 26 bank（本轮只做了块 0），看是哪个 bank 在运行中变了。

**已修**：哨兵从 `bank 13` 挪到 **`bank 30`**（`SENTINEL_BANK`，在 BN 槽 0..23 与 CN 结果
10..12 之外）。`run-pdsch-bg2` 与 `run-pdsch-gather` 重跑仍全对，但**这消除了"8 次迭代时
第二轮 CN 哨兵被上一轮 BN 覆盖"的隐患**。

下一步（明确）：块 1 BN 前/后各 dump 26 bank + 逐 bank diff，即可定位到具体 bank/槽。

**块 1 前/后 26 bank 逐 bank diff（本轮结论，关键）**：

| 区域 | 结果 |
|---|---|
| BN 前 spad（26 bank × 20） | **0 个 bank 不同** |
| BN 后 spad | 起初只有 **bank 23** 不同 —— 因为 BN 微码会写**全部 24 个槽**（含补零槽），而判据只建模了真实边、把补零槽留在 0 |
| 判据改成"补零槽也写 `v − 0`"后 | **0 个 bank 不同** |

所以之前若干轮里"块 1 BN 输出 384/若干差异"是**判据的伪差异**（漏建模补零槽），
不是硬件错误。修正后块 0、块 1 在"两块串行"里前后 spad 都逐值对齐。

但把块数扩到 52 时，硬判决仍有 ~867 处不同，说明**还有一处与块序号相关的差异**；
结合"块 0/块 1 精确"，怀疑是后续块的 gather 读取了被前块 scatter 改写过的那部分
`msg[r][k]`（即 scatter 的逆映射写到了别的块的边上）。下一轮直接把 scatter 后的
`msg` 与模型对比（而不是只看 hard），即可确认。

本轮调试文件已回退，仓库保持绿色。

**本轮（按"块 1 前后 26 bank + 逐 bank diff"执行）的关键结果**：

| 区域 | 结果 |
|---|---|
| BN 前 spad（26 bank） | **0 bank 不同** |
| BN 后 spad | **0 bank 不同**（模型按"补零槽也写 v−0"口径） |
| **scatter 之后的 `msg`** | **338 处不同** ❌ |

也就是说：**BN 本身完全正确**（前/后 spad 全部逐值一致），**最后一个错误点在 scatter**
（把 BN 输出写回 `msg[r][k]` 时，`(i + sh) % Zc` 的映射仍与模型不一致）。这正好解释了
"块 0/块 1 单独正确、52 块串行时后续块输入被前块写坏"的现象。

下一步（已收敛到一个表达式）：把 scatter 的三处可能写法（`(i+sh)`、`(i−sh)`、恒等）
在**同一份 BN 输出上**逐一对照硬件 dump，取差异为 0 的那一个即可收尾。

**三种 scatter 写法逐一对照（离线用同一份 dump 复算）**：

| 写法 | 差异数 |
|---|---|
| `msg[i] = post[(i+sh)%Zc]`（当前实现） | 338 |
| `msg[i] = post[(i−sh)%Zc]` | 356 |
| `msg[i] = post[i]`（恒等） | 356 |

**三者都不是 0** —— 说明硬件 scatter 之后写进 `msg` 的内容与 BN 输出（我们已逐值验证过）
之间不存在"简单旋转"关系。最可能的是**基准自身的问题**：scatter 循环里的 `n`/`m` 与
dump 循环共用、或 dump 时机（DMA out 之后/散射之前），而不是映射公式。

下一轮先用最小改动验证：在 scatter 后立刻读回 `msg` 并**与 `bout` 直接比对**（不经过模型），
若也差，则问题在 scatter 的循环变量；若相等，则模型/期望值写错。

**直接比对（不经过模型）：scatter 后的 `msg` vs 硬件自己的 BN 输出**：

对每条边，在 26 个槽 × 20 种旋转里搜"能完全复现硬件 `msg`"的组合：

| 边 | (r, k, sh) | 匹配结果 |
|---|---|---|
| 0 | (0,1,0) | **无任何 (slot, rot) 匹配** |
| 1 | (2,1,94) | 无匹配 |
| 2 | (3,0,38) | 无匹配 |
| 22（最后一条） | (41,0,**0**) | **(slot 22, rot 0)** ✅ |

即：**只有 sh = 0 的那条边**能对上，其余边在 26×20 种组合里都对不上。

结合"BN 输出本身逐值正确"，说明 scatter 写进 `msg` 的值**既不是 BN 输出的任何旋转、
也不是旧值**——更像是**散射循环里读错了 `n`/缓冲**，或**dump 与 scatter 的次序**问题。

下一步（最后一步）：把 scatter 改写成"先算到临时数组、再一次性拷回"，并在 scatter 前后各
dump 一次同一条边的 `msg`；若此时前后都不变 → 说明 scatter 没执行；若变但不对 → 看 `n` 的取值。

**改成"临时数组再拷回"后的实测**：

| 比较 | 结果 |
|---|---|
| `msg` vs 临时数组 `tmp`（拷回是否正确） | **0 差异** ✅ |
| `tmp` vs `bout`（恒等） | 160 —— 正常，因为 `tmp` 施加了 `(i+sh)` 旋转，`sh=0` 的边全是 0 差异 |
| `msg`（硬件）vs 模型 `post` | 仍对不上（前一轮 338） |

结论：**scatter + 拷回本身完全正确**，`msg == tmp`；而 `tmp` 是 `bout` 的旋转。

所以剩下的唯一嫌疑是 **`bout` 与 spad 里的 BN 输出不一致**（即 **DMA out（spad→RAM）**
没有把 spad 的内容原样搬回）——之前 `run-pdsch-gather` 里 `bout` 是对的，但那一次的路径
不同（单块、无散射）。下一步：在同一次运行里**同时 dump spad-after 与 `bout`**，
两者一比对即可确定是不是 DMA out 的问题。

**同一次运行里 spad-after vs bout**：

```
spad-after vs bout diffs: 348
bout[0][0] = 691  （模型算出的正确值 v − m = 691，且它不在 spad 的任何位置）
spad[0][0] = -535 = v − 0   （说明 BN 运行时 slot 0 的输入是 0）
```

结论：**spad 里 BN 跑的那份输入缺了 slot 0（读到的是 0），而 RAM 的 `bout` 是按正确输入算出来的**
（bout 是 DMA out 前的 spad？不，是 DMA out 的结果）。两种解释合在一起只剩一个：

> **DMA in（RAM→spad）没把 gather 缓冲的第 0 行搬进去**（或搬到了别处），
> 于是 BN 用 0 当 slot 0；而 `bout` 的 691 恰好等于"用正确输入算出的值"，
> 说明 `bout` 里其实是**上一轮/另一份数据**。

这解释了全部现象（含 52 块串行失败）。下一步：在 **DMA in 之后立刻**（BN 之前）dump
spad 第 0 行并与 `gath[0]` 比对——之前这一比对是在旧版本里做的（当时通过），
需要在新版本重做；若这次不相等，问题就在 520 词 / 26 行的 2D 搬运边界上。

**DMA-in 单独验证（同一份 26×20 缓冲，无 CN、无 BN）**：

```
spad vs gath after DMA-in: 0 diffs
```

即 **RAM→spad 的 2D 搬运（520 词 / 26 行 / stride 32）完全正确**。

结合上一轮"spad-after 的 slot 0 像是 `v−0`"，差别只在**是否先跑过 42 个检查节点的 CN 通道
和块 0 的 BN**。因此剩下的怀疑是**前序操作对 spad/页状态的影响**（而不是 DMA 引擎本身）：

- CN 通道把结果 DMA 出到 `res`（从 spad bank 10 起），BN 再往 bank 0..25 写；
- 两者之间没有显式的页切换/清零。

下一步：在这个"有 CN、有块 0"的版本里，**DMA in 之后立刻 dump spad 与 gath 比对**
（本轮的无 CN 版本已验证 0 差异），若此时不一致，就能定位到"前序操作污染"的具体位置。
