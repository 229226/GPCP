# 20 — 协议基准方案（HLL 描述 → 一键编译 → 真实负载评估）

> **状态：生效（2026-11-09）**。本文件是"写 benchmark"的唯一规范。
> 与 `docs/14`（自研编译器方案，搁置）的关系：那份是"给 C 加后端"，本文件**不是**那条路。
> 任何 AI/开发者新增或修改 benchmark，都必须按本文件执行；违反第 3 节的规则会被
> `make proto-check` 直接拦下。

---

## 0. 两条硬约束（一切设计围绕它们）

| 约束 | 含义 | 可执行证明 |
|---|---|---|
| **B1 硬件无关** | 协议描述里不许出现任何芯片概念（存储块、页、并行单元、拍数、搬运、指令内存） | ①`check_hll.py` 语法树禁用词/白名单；②**换厨房测试**：同一份场景对两种 target 编译，源码逐字节不变、生成物不同、都能过自检 |
| **B2 真实负载** | benchmark 不是"跑一次算对"，而是按真实时隙节奏连续跑，看能否按时完成 | ①`load.py` 的时隙时间轴（1 ms/格）；②门禁主判据 = 按时率；③报告必须含"差距表" |

**为什么不做 C 前端**：`docs/14/15/16` 已实测证伪（Morpher 后端对 20 节点 0 个可编码；II=4 是架构差异）。
本方案的"编译"只负责：语义图 → 资源无关调度 → **按 target.yaml 落点** → 生成微码与编排。

## 1. 三层结构（每层都不许提硬件）

```
L3 场景 scenario   ：协议参数 + 发射/信道/接收的动词序列 + 判据 + 负载档
L2 图   graph      ：由动词序列记录出的节点图（算子、张量、依赖、协议属性）
L1 算子 kernel     ：cgra/kernels/*.yaml（已有 31 份，自带 ISA 周期级对拍）
```

- L2/L3 里**只能**出现本文件第 2 节的动词与协议量。
- 硬件真相只在 `cgra/target.yaml`；换算只在 `cgra/tools/target.py` 与 `proto/lower.py`。
- 微码只由 `gen_kernel_prog.py`（编译器）产出（沿用 AGENTS §4.18）。

## 2. 唯一合法动词表（v1，冻结）

`S = scenario(name, rat, direction)` 之后，只允许下列方法。新增动词必须提"规范修订"
（见 §8），不允许在场景文件里自定义函数。

| 动词 | 语义（协议含义） | 生成什么 |
|---|---|---|
| `S.cfg(**kw)` | 协议配置（带宽、子载波间隔、调制阶数、用户数…）。**其余量必须由这里推导** | `cfg.derived`：RB 数、FFT 点数、CP 长、可用 RE、TB 比特、码块数、提升长度 |
| `S.traffic(**kw)` | 业务到达模型（泊松/ON-OFF、目标利用率、MCS 分布、NACK 率） | 每时隙的"该干什么"清单（供负载模型驱动） |
| `S.transport_block(bits, rnti)` | 一段传输块 | 张量 `tb` |
| `S.received(kind, length)` | 接收波形来自激励（外部设备已发过），本程序不生成 | 张量 `wave` |
| `S.encode(x, scheme, **kw)` | 信道编码（LDPC / Polar） | 张量 `cw` |
| `S.modulate(cw, qm, scrambler)` | 加扰 + 调制 | 张量 `sym` |
| `S.dmrs(type, n_id, l)` | 解调参考信号序列 | 张量 `ref` |
| `S.correlate(src, ref, hypotheses, seq)` | 相关搜索（PRACH 的循环移位、PUCCH 的 m_CS、SSB 的 PSS/SSS 假设） | 张量 `corr`（每个假设一个能量） |
| `S.map_to_grid(sym, dmrs)` | 资源映射（含导频位置、DC、保护带） | 张量 `grid` |
| `S.extract(grid_like, **kw)` | 从网格取 RE | 张量 `re` |
| `S.measure(grid, ref, report)` | 用参考信号做信道/干扰测量，给出上报量（CSI 的宽带 CQI） | 上报值 |
| `S.ofdm_modulate(grid)` | OFDM 调制（含 CP） | 张量 `wave` |
| `S.ofdm_demodulate(wave)` | OFDM 解调 | 张量 `grid` |
| `S.channel(wave, model, **kw)` | 信道（AWGN / 两径 / 平坦衰落） | 张量 `y` |
| `S.estimate(y, ref)` | 信道估计 | 张量 `h` |
| `S.equalise_demap(y, h, qm)` | 均衡 + 软解调 | 张量 `llr` |
| `S.mimo_equalise(y, h, qm, layers, rx)` | 多天线均衡（MMSE）后硬判 | 张量 `hard` |
| `S.decode(llr, scheme, max_iter)` | 信道译码 | 张量 `hard` |
| `S.expect(**anchors)` | 判据（逐元素对账） | `golden.json` 的断言项 |
| `S.budget(**kw)` | 实时预算（每时隙毫秒数、按时率下限、阶段占比上限） | 门禁阈值 |

> `max_iter` 是**算法参数**（协议与实现共有），不是硬件参数；`qm`、`rv`、`slot_ms` 同理。

> **v1.1 参数扩展（2026-11-09，多制式批次）**：不新增动词，只扩展参数取值——
> `decode(scheme=)` 追加 `"conv"`（K=7 BCC，EHT-SIG）与 `"ldpc_wifi"`
> （IEEE 802.11 N=648/Z=27，rate 1/2）；`correlate(seq=)` 追加
> `"lte_pss"` / `"lte_sss"`；`dmrs(type=)` 追加 `"wifi_ltf"`。
> 版本基线：NR Rel-19、LTE Rel-18、IEEE 802.11be-2024。

## 3. 禁止清单（`make proto-check` 强制，违反即失败）

1. **标识符禁用词**（大小写不敏感）：`spad` `bank` `page` `pe` `imem` `cycles`
   `dma` `descriptor` `tile` `latency` `paddr` `addr` `mmio` `instruction` `microcode`。
2. **语句白名单**：只允许 `Assign` / `For` / `If` / `Expr(调用)` / 模块级常量赋值。
   禁止 `while` / `try` / `class` / `lambda` / `global` / `with` / `import`（除 `hll` 一行）。
3. **调用白名单**：只能调用第 2 节动词 + 内建 `len/min/max/range/int/bool`。
   自定义函数、第三方库一律拒绝。
4. **不许有副作用**：不许读写文件、不许打印、不许改全局。
5. **不许手填物理量**：不允许出现"点数值"的存储坐标、拍数、描述符字段；
   协议常量（如 24 比特 CRC、80 比特 TB、720 比特 E）可以出现，且必须来自 `cfg` 推导或动作参数。

## 4. 产物契约（生成物固定格式，便于横向比较）

`build/proto/<scenario>/` 下：

```
ir.json         语义图（与 target 无关，可 diff：同一场景两个 target 必须逐字节相同）
plan-<target>.json  落点结果：每阶段的 tiling / 并行度 / 缓冲需求 / 可行性诊断
stimulus.bin    激励（只含协议输入：TB、rv、RNTI、SNR、seed…不注入黄金符号）
golden.json     判据锚点（由 Python 模型算，供 checker 用）
report.md       评估报告（按时率、最差时隙、阶段占比、差距表）
```

**结果区约定**（所有新 benchmark 统一，不再各自为政）：
`[0] marker, [1] errors, [2] cycles, [3] array_runs, [4] dma, [5] busy_cycles,
[6] irq, [7] overrun, [8] params_hash, [9] 0x600D, [10..] payload`

## 5. 负载模型（B2 的落点）

### 5.1 时间轴
按 `slot_ms` 推进（µ=0 → 1 ms；µ=1 → 0.5 ms），默认跑 40 格；
逐格记录"是否在预算内完成"，SSB/PRACH/CSI 按各自周期插入。

### 5.2 负载档（参数由 `cfg` 推导，不写死）

| 档 | 配置 | 每格内容 | 用途 |
|---|---|---|---|
| L1 轻 | 20 MHz / µ=0 | 1 UE、QPSK、1 TB | 日常回归（快） |
| L2 中 | 50 MHz / µ=1 | 2 UE、16QAM、HARQ 8 进程、10% NACK | 调度与重传 |
| L3 重 | 100 MHz / µ=1 | 4 UE、64QAM、SSB+PDCCH+PDSCH | 满负载（差距表） |
| L4 上行 | 100 MHz / µ=1 | L3 + PUSCH（含 DFT-s）+ PUCCH + SRS | 双向压力 |

### 5.3 评分（门禁主判据）
`按时率 ≥ 阈值`（默认 1.0，L3/L4 允许 0 但必须出差距表）、`errors == 0`、
`逐元素对账全过`、`阶段占比/差距表`必须打印。

## 6. 一键命令

```bash
make proto-check                 # 只跑静态检查（禁用词 / 白名单 / 换厨房）
make proto PROTO=nr_pdcch        # 生成 → 检查 → 编译 → 跑 → 评估 → 记台账
make proto-all                   # 所有场景 × 负载档，出汇总表
```

`make proto` 的步骤与断言（缺一不可）：
1. `check_hll`：§3 全部规则
2. `compile`：场景 → `ir.json`（**同一场景对不同 target 的 ir.json 必须逐字节相同**）
3. `lower`：`ir.json` + `cgra/target.yaml` → `plan-*.json` + 可行性诊断（不可行则报缺什么）
4. 生成微码（调用现有 `gen_kernel_prog.py`）与 `plan.h`（`proto/emit.py`：阶段表 +
   参数摘要 + 每时隙预算；同时产出 `stimulus.bin` 与 `golden.json`）
5. 编译裸机程序（`sw/soc/proto_runner.c`，按 plan.h 的阶段表执行）→ 仿真 → 结果
6. `proto_eval`：判据 + 按时率 + 差距表 → `report.md`；阶段 0 还要与手写 benchmark
   逐值对账（`--ref auto`）。记账证据行由报告给出，**用 `tools/devlog.py` 录入**
   （`docs/dev-log.csv` 不允许手写，见 AGENTS §10）

## 8. 给 AI 的开发规则（改这个方案时必须遵守）

1. **加动词**：先在 `proto/hll.py` 实现 + 在本文 §2 加一行 + 给出该动词的 golden 对拍；
   一次提交只加一个动词。
2. **改动词语义**：必须重跑 `make proto-all`，并在提交信息里写"旧场景结果是否变化"。
3. **降级禁令**：任何场景文件里出现的硬件词，不允许通过"改检查器"绕过；只能改
   `lower.py`（把决定权交给编译器）。
4. **不许复制现有 C benchmark**：新场景必须走 `make proto`；手写 C 只允许出现在
   `sw/soc/proto_runner.c`（通用运行器）与已登记的算子实现里。
5. **每个阶段都要在 `verify.sh` 里有门**：`proto-check` 进 quick 档；
   `proto` 真实仿真进 full 档（`PROTO=` 参数化，避免仿真时长失控）。
6. **批量编写、统一验证（2026-11-09 定）**：同一批 benchmark 必须**先全部写完**
   （场景 + 模型 + 实现库），再跑一次 `verify full`；**不要**每写一个就跑一次门禁。
   门禁只在两种情况单独跑：① 批量验证失败后定位；② 改动了共享实现库
   （`*_stages.inc` / `proto/proto_eval.py`）。批量提交时按"一批一个提交"，
   提交信息里列出本批全部场景名。
