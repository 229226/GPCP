# 21 — 从 87% CPU 时间到阵列：算法下沉与主机接口加宽方案

> 依据：`perf-report.html` / `perf-summary.csv`（17 个协议场景、114 个阶段的互斥周期账本）。
> 目标：在不增加 PE 数量的前提下，把 CVA6 上的算法与数据搬运下沉到 CGRA，并把主机接口从“逐字 MMIO”升级为“批量 DMA + 任务描述符”。
> 本文只给方案与验收口径，不改代码；实施时每一步都必须过 `make proto-check` 与 `tools/verify.sh full`。

---

## 0. 结论摘要

### 0.1 现状（阶段账本合计）

| 项目 | 周期 | 占比 |
|---|---:|---:|
| 阵列执行 | 2,268,217 | 4.7% |
| DMA 传输 + 等待 | 3,874,837 | 8.0% |
| CPU 执行 | 42,271,040 | 87.3% |
| 其中 CPU 标量算法 | 41,679,304 | 86.1%（占 CPU 98.6%） |
| 其中 IMEM/配置/缓存 | 591,736 | 1.2%（占 CPU 1.4%） |

> 整跑总计 48,578,703 周期；上表为 114 个阶段之和 48,414,094，差值 164,609 为循环与收尾开销。

两条硬结论：

1. **瓶颈不是主机配置，而是算法本身跑在 CVA6 上。** IMEM 装载、阵列/DMA 配置、缓存维护合计只占 CPU 的 1.4%；即使把主机接口做到零开销，也只能解决 1.4%。
2. **主机接口仍然是必要前提。** 算法下沉后，数据进出、描述符序列、完成同步都会放大；不先把“逐字 MMIO + 每行一次启动”改成“批量 DMA + 任务链”，下沉后的阵列会被 CPU 编排重新拖住。

### 0.2 目标（保守区间）

| 指标 | 现状 | 目标 |
|---|---:|---:|
| 17 场景总周期 | 48.6M | 20–24M |
| CPU 占比 | 87.3% | 45–55% |
| 阵列占比 | 4.7% | 20–30% |
| LDPC 单块阵列运行 | 752 次 | ≤ 120 次 |
| LDPC bank 冲突/阵列忙 | 25.5% | < 10% |
| 峰值 Fmax | 1.05 GHz | ≥ 1.0 GHz（不退化） |

### 0.3 优先级

| 顺序 | 方向 | 预计节省 | 工作量 | 依赖 |
|---|---|---:|---|---|
| P1 | DFT/IDFT 200/360 下沉 | 8.9–10.0M | M | 无 RTL |
| P2 | LDPC 重构/旋转下沉 + bank 布局 | 5.7–6.7M | L | spad 旋转表 RTL |
| P3 | FFT4096 编排/搬运瘦身 | 3.0–3.8M | S–M | 无 RTL |
| P4 | Turbo 译码下沉 | 4.3–4.7M | M | 无 RTL |
| P5 | QAM/加扰向量化 | 2.3–2.6M | S | 无 RTL |
| P6 | 主机 64-bit / 写合并 / 任务链 | 1.5–2.0M（直接）+ 使能上述各项 | M–L | SoC 接口 RTL |
| P7 | Polar/SSS/WiFi LDPC/DFT256/小区搜索 | 3.1M | M | 视 P1 复用 |

如果只做三件事：**先做 P1**（收益最大、无 RTL 风险），**同时做 P3 的软件先手**（IMEM 批量装载 + 描述符模板，立刻见效），**再做 P2**（需要 RTL，但决定 LDPC 能否真正实时）。

### 1.1 按制式

| 制式 | 总周期 | 阵列占比 | CPU 占比 |
|---|---:|---:|---:|
| LTE | 16,018,017 | 2.3% | 94.2% |

### 1.2 关键判断

- **LTE 更严重**：阵列几乎不用（2.3%），Turbo/DFT/调制全在 CVA6；先把 LTE 的 DFT200 与 Turbo 做掉，收益最直接。
- **NR 的 LDPC/FFT 是“阵列在跑，CPU 在伺候”**：LDPC 阵列只忙 6%，CPU 82.8%；FFT 阵列 13.2%，CPU 66.4%。这不是 PE 不够，是编排和数据搬运太重。
- **WiFi 的“阵列 kernel”名不副实**：`wifi_ldpc_z27` / `dft256_radix2` 的阵列忙为 0，实际是标量实现；要么改落点，要么改名字，不能让它继续占用“已下沉”的预算。
- **“配置只占 1.4%”是下界**：`fe_load` 这类直接逐字写 IMEM/SPAD 没有走公共运行时函数，仍被计入“标量算法”；主机接口的真实成本被低估，B 的收益要按 §3.4 的分解估算，而不是只看 1.4%。

## 2. 方案 A：算法下沉

### A1. DFT/IDFT 200/360 点 → CGRA

#### 现状

- `nr_pusch_tp`：`equalise_demap` 5,052,600 周期 / 2 符号 = **2.53M 周期/符号**（360 点 IDFT）。
- `lte_pusch`：`modulate` 3,078,216 + `equalise_demap` 3,110,821，各含 200 点 DFT/IDFT，均约 **1.5M 周期/符号**。
- 实现是朴素 O(N²)：`idft360`（`sw/soc/pusch_stages.inc`）与 `lu_dft200` / `lu_idft200`（`sw/soc/lte_ul_stages.inc`）。
  360² = 129,600 次复数乘加，且带 64-bit 乘、取模、除法，单次成本约 19 拍；200² = 40,000 次，单次约 39 拍。

#### 落点设计

**首选：Bluestein → 512/1024 点 FFT，复用现有 `fft4096` 引擎。**

- 360 点：`M = 1024`；200 点：`M = 512`。预计算 chirp 表 `exp(-jπn²/N)` 与 FFT 旋转因子，放 RAM，按 tile 搬入 spad。
- 新增 kernel：`dft360_bluestein`、`dft200_bluestein`（正向/反向共用，反向取共轭）。
- 结构：3 次 M 点 FFT（前向、点乘、反向）+ 1 次点乘；复用 `fft_stage` / `fft_block` 微码与描述符模板。
- 数据布局：输入 `int16` 复数对（I/Q 各 16 bit），按 32-bit 打包；chirp 与旋转因子按 spad 32 bank 布局，避免同 bank 冲突。
- 输出直接写 LLR/软符号顺序，省掉 CPU 的 `>>` 定标与重排。

**备选：混合基 2/3/5 直接 kernel。**

- 360 = 2³×3²×5，200 = 2³×5²；分解成小点数蝶形，延迟更低，但微码与验证量更大。
- 建议先用 Bluestein 拿到 5–10× 收益，再评估是否需要混合基压延迟。

#### 预期收益

| 阶段 | 现状 | 目标 | 节省 |
|---|---:|---:|---:|
| `nr_pusch_tp equalise_demap` | 5.05M | 0.8–1.2M | 3.9–4.3M |
| `lte_pusch equalise_demap` | 3.11M | 0.6–1.0M | 2.1–2.5M |
| `lte_pusch modulate`（DFT 部分） | ~2.5M | 0.5–0.8M | 1.7–2.0M |
| 其他场景的 DFT 部分 | ~1.4M | 0.3M | 1.1M |
| **合计** | **~12.1M** | **2.1–3.2M** | **8.9–10.0M** |

#### 验收

- 与当前整数 DFT 逐值对齐：软符号允许 ±1 LSB，硬判决/LLR 符号必须完全一致。
- `nr_pusch_tp` 与 `lte_pusch` 两个 proto 场景的 `equalise_demap` 阶段周期达标；`verify full` 无回归。
- 阵列 bank 冲突 < 10%（chirp/旋转因子布局要专门检查）。

### A2. LDPC：把重构、旋转、gather/scatter 全部下沉

#### 现状

- 每个 BG2/Zc=20 码块 8 次迭代：**752 次阵列运行 / 1556 次 DMA**，CPU 10.12M（占 kernel 82.8%），标量 9.57M。
- `reconstruct_gather` 每个元素约 26 拍（4 次 load + 1 次 store + 约 10 条 ALU），是标量时间的主体。
- `bn_scatter` 是逐边旋转拷贝；`docs/09` §5.4 已证明：当前 ISA（静态微码、spad word 立即数）和拷贝引擎（仅 stride/row）都表达不了“每边不同旋转量”。
- bank 冲突已达阵列忙的 25.5%，说明现有布局本身也有问题。

#### 落点设计（RTL + 布局 + 微码三件事）

**R1. spad 地址加“每 bank 旋转表”**（`docs/09` §5.5 的候选）

- 32 个 bank 各一个 5-bit 旋转量寄存器：`0x5000_0200 + 4*bank`（W/R）。
- `Zc` 寄存器：`0x5000_0240`（W/R，默认 20/64）。
- 指令增加一位“参与旋转”标志（建议用 imm bit15）；有效地址：
  `addr = base + (((word + rot[bank]) % Zc) * 4)`。
- 代价：`cgra_pe.sv` 地址通路加 32×5 bit 寄存器堆 + 一个 5-bit 加法/比较；面积增量小，但**所有 kernel 的地址语义要回归**。

**R2. 消息布局改 block-major**

- `msg[r][k][i]` → `msg_b[b][e][i]`（b = 变量块，e = 该块的边）。
- BN 输入按 `-sh` 读、输出按 `+sh` 写；CN 输出直接写重构后的边消息。
- 这样 `reconstruct_gather` 与 `bn_scatter` 整趟消失，CPU 不再逐元素碰消息；DMA 只按块搬（197 条边 × 73.7 拍 ≈ 14.6k 拍/迭代，见 `docs/09` §5.3 实测常数）。

**R3. CN/BN 微码融合 + 行/列循环内收**

- CN 程序在算完 `min1/min2/sign` 后，直接用旋转表把边消息写到 BN 的 block-major 布局；不再输出中间 `res_r`。
- BN 程序直接读旋转后的输入、写旋转后的输出；硬判决单独走一块。
- 把 42 行 / 52 列的行循环也收进微码（行计数器 + 旋转表），每迭代只启动 **CN 一次、BN 一次**；8 次迭代 16 次阵列运行，加硬判/收尾 ≤ 120 次/码块（现状 752 次）。
- 目标：每迭代 CN 27.3k + BN 49.2k ≈ 76k 拍（`docs/09` §5.5 估算），对比当前约 245k 拍/迭代。

**R4. bank 布局先修**

- 在 R2 之前先做一次 spad swizzle：把 24 个消息槽按 `slot ^ (bank & 3)` 之类的轻量置换，目标把 25.5% 的 bank 冲突压到 10% 以下。
- 如果 swizzle 不够，再评估加 bank（面积代价）——但优先用布局解决。

#### 预期收益

| 项目 | 现状 | 目标 |
|---|---:|---:|
| LDPC kernel 总周期 | 12.23M / 7 实例 | 5.5–6.5M |
| 其中 CPU | 10.12M | 1.5–2.5M |
| 阵列运行/码块 | 752 | ≤ 120 |
| bank 冲突/阵列忙 | 25.5% | < 10% |

#### 验收

- 1040/1040 硬判决、80/80 TB、CRC、syndrome 0 全部保持。
- `run-pdsch-iter` / `run-pdsch-full` / `run-pdsch-harq` / `run-pdsch-zc64` / `run-pdsch-bg1-zc64` 全过。
- 8 次迭代总周期与 `docs/09` 的成本模型偏差 < 15%。

### A3. FFT4096：先砍编排，再砍搬运

#### 现状

- 17 个实例，CPU 7.16M（66.4%），标量 7.15M；每个实例约 420k CPU 周期。
- `sw/soc/ssb_fft.inc` 的 `fe_load()` 用 `gpcp_cgra_write` **逐字写 IMEM**；`fe_desc_stages()` 每次调用重新构造约 768 个描述符；`fe_exec()` 每个 tile 都重设 ring、两次等待。
- 数据打包（int16→int32、CP、定标）也在 CVA6 上。

#### 落点设计

**S1. IMEM 改 DMA 批量装载（软件，立即做）**

- 把 `fe_load()` 的逐字写改成 `gpcp_cgra_imem_load()`；`docs/10` §13 已实测 2,480 字从 18,248 拍降到 8,484 拍（2.15×）。
- 预期：每个 FFT 省 10–20k 拍，17 个实例约 0.2–0.3M。

**S2. 描述符模板复用（软件）**

- FFT 的 tile 序列只由 `n`、tile 数、stage 数决定；在第一次调用时生成一次描述符数组，后续符号复用，只改 `ram` 指针。
- 预期：省掉每符号 768 次描述符构造，约 1.5–2.5M。

**S3. 批量数据搬运（软件 + 现有 DMA）**

- 打包/解包改成 2D DMA：`stride/row` 直接表达“每符号 256 点、行跨 4096”；避免逐字 `mmio_w`。
- 预期：0.5–1M。

**S4. 任务描述符（与 B2 合并）**

- 把“DMA in → array → DMA out”做成一个复合描述符，CPU 每 tile 只写 1 条而不是 5+ 条；FFT 112 次运行/符号降到 1 次任务提交。
- 预期：再省 1–1.5M。

#### 验收

- 4096 点 FFT 逐位一致（`run-fftprobe`）。
- `ofdm_modulate` / `estimate` / `ofdm_demodulate` 阶段 CPU 占比从 66–99% 降到 < 40%。
- 单次 FFT 的 CPU 周期 < 250k（现状约 420k）。

### A4. LTE Turbo 译码 → CGRA

#### 现状

- `turbo_k104` 4 个实例（编码 2 + 译码 2），5.59M，100% 标量；单次译码约 2.75M。
- K=104、8 次迭代、Max-Log-MAP；状态数 8，天然适合 16 PE。

#### 落点设计

- 新 kernel `turbo_decode_k104`：8 个状态 × 2 个半窗，16 PE 各负责一个状态/分支；分支度量用 int16，外信息 int16 存 spad。
- 滑窗：每个窗 32 个 trellis 步，前向/后向各 16 PE；窗间用 DMA 搬边界度量。
- 交织/解交织用表驱动 DMA（现有 `stride/row` 不够时加一维描述符）。
- 若阵列映射效率不达预期，退路是做一个专用 Turbo 小引擎（8 状态 ACS 阵列），但优先复用 CGRA。

#### 预期收益

- 单次译码 2.75M → 0.3–0.5M；4 个实例 5.59M → 0.9–1.3M。
- LTE PUSCH/PDSCH 的 CPU 占比从 94%/91% 降到 60% 左右（与 A1 叠加后更低）。

#### 验收

- 与现有 `tools/lte_turbo.py`（或当前 C 模型）逐位一致；BER 曲线在相同 SNR 下不退化。
- 8 次迭代、K=104、码块边界与 tail bits 全部对齐。

### A5. QAM/加扰向量化

#### 现状

- `scalar:modulate` 3.34M / 4 实例；LTE PUSCH 单场景 3.08M，含 QPSK 映射、Gold 加扰、200 点 DFT。
- 逐比特循环 + Gold LFSR，指令数受限。

#### 落点设计

- 新 kernel `qam_map`：16 PE 并行处理 16 个符号；QPSK/16QAM/64QAM 用同一套分支度量表。
- Gold 序列：每 PE 一个 LFSR，或预生成 1 个 slot 的 Gold 表放 spad（按需选）。
- 加扰与映射融合，输出直接进 DFT 输入缓冲，省一次 CPU 重排。
- 与 A1 的 DFT200 共用数据布局。

#### 预期收益

- `scalar:modulate` 3.34M → 0.7–1.0M；若 DFT200 同时下沉，LTE PUSCH `modulate` 从 3.08M 降到 < 0.6M。

#### 验收

- 与现有 `nr_qam.py` / QPSK 黄金模型逐符号一致；64QAM 三阶功率归一化不变。
- `nr_pdsch_16qam` / `nr_pdsch_64qam` / `lte_pusch` 全过。

## 3. 方案 B：主机接口加宽

> 注意：实测 CPU 配置只占 1.4%，所以 B 的直接收益有限；B 的价值主要是**让 A1–A6 下沉后不被数据搬运重新拖住**。先做 B1/B2 中“软件能立刻用”的部分，再做 RTL。

### B1. 数据面：从逐字 MMIO 到批量 DMA

#### 现状常数（`docs/09` §5.3 实测）

| 操作 | 实测 |
|---|---:|
| CPU 顺序写 RAM | 4.0 拍/字 |
| CPU 顺序读 RAM | 6.3 拍/字 |
| spad MMIO 写 | 16 拍/字 |
| spad MMIO 读 | 23 拍/字 |
| DMA 500 字 RAM→spad（2D） | 391 拍/次 ≈ 0.78 拍/字 |
| DMA 20 字（小传输） | 73.7 拍/次（固定开销主导） |
| IMEM 装载 2,480 字 | 1,825 拍/次（逐字写时 18,248 拍） |

#### B1.1 软件先手（无 RTL）

- 新增 `gpcp_cgra_spad_write(ram, spad_idx, words, stride, row)` / `spad_read` 封装，内部走现有 DMA；所有 ≥ 64 字的整块搬运改用它。
- `fe_load` 改 `gpcp_cgra_imem_load`（见 A3-S1）。
- 所有“逐字 `mmio_w` 写 SPAD”的循环改成“先在 RAM 组包，再一次 DMA”。
- 预期：直接省 1–2M；同时把标量算法里的“主机窗口拷贝”暴露出来，便于后续测量。

#### B1.2 64-bit 主机写口（RTL）

- `cgra_top` 的 `wr_data` 从 32 位扩到 64 位，增加 `wr_strb[7:0]`；地址 8 字节对齐。
- SPAD 一次写两个 word（bank 相邻或同 bank 两个 word，按布局选）。
- 软件 ABI 加 `mmio_w64()` / `gpcp_cgra_write64()`；未对齐访问拆成两次 32 位。
- 预期：对齐的流式拷贝 2×；面积/时序代价小，但 SoC 桥要改。

#### B1.3 写合并 FIFO（RTL，可选）

- 在主机口前加 8–16 项 64-bit write-combining FIFO；连续地址自动合并成 burst。
- 必须在 `fence`、读操作、上下文切换时 flush；语义要写进 ABI。
- 预期：流式写 4–8×；风险是顺序/可见性，建议在 B1.2 之后做。

### B2. 控制面：从“每行一次启动”到“任务链”

#### 现状

- LDPC：752 次阵列运行 + 1556 次 DMA/码块；FFT：112 次阵列运行/符号，约 768 个描述符/次。
- CPU 每次都要写 ring 寄存器、等 done、再启动阵列；这些周期落在“CPU 标量/配置”里。

#### B2.1 复合任务描述符（RTL）

在现有 8-word DMA 描述符之后追加 8-word“阵列任务头”，形成一个 16-word 复合描述符：

```text
[0]  ctrl        {bit0 dma_in_en, bit1 array_en, bit2 dma_out_en, bit3 next_en}
[1]  dma_in_src  RAM 地址
[2]  dma_in_dst  {spad_idx[15:0], page, len[15:0]}
[3]  array       {cycles[15:0], page, prog_id}
[4]  dma_out_src {spad_idx, len}
[5]  dma_out_dst RAM 地址
[6]  repeat      {count[15:0], stride, row}
[7]  next       下一个描述符地址（0 = 结束）
[8..15]         预留（旋转表基址、bank 掩码等）
```

- CGRA 内部小 FSM 按 `dma_in → array → dma_out → next` 自动执行；CPU 只写描述符、按一次 start。
- ring 深度 8–16；LDPC 的 42 行/52 列、FFT 的 16 tile 都可以用 `repeat` 展开。
- 预期：LDPC 配置 0.51M → < 0.1M；FFT 描述符构造 1.5–2.5M → < 0.3M。

#### B2.2 完成通知

- 增加 done FIFO（深度 16）或中断聚合；CPU 不再逐次轮询 `STATUS`。
- 对当前基准（CPU 没有别的事可做）主要省的是 issue 周期与延迟；对真实协议栈（CPU 要跑 MAC/RRC）价值更大。
- 保持现有轮询路径作为兼容模式。

#### B2.3 描述符/微码预置

- IMEM 与 PE preload 都走 DMA；新增“预置描述符”命令，把常用 kernel 的 IMEM 镜像常驻，避免每次重装。
- 预期：LDPC 每次迭代的 IMEM 装载（1,825 拍 × 2）可省一半。

### B3. 地址映射与一致性

- 给 SPAD/IMEM 增加一个**非缓存、可写合并**的 1 MB 窗口；CPU 用 64-bit store，DMA 与 CPU 的可见性用 `fence` 定义。
- 保留现有逐字窗口作为调试/小数据路径。
- 所有 DMA 目标页与阵列页的 ping-pong 规则不变（docs/07 §4）。

### B4. 预期收益

| 项目 | 现状 | 目标 | 节省 |
|---|---:|---:|---:|
| CPU 配置（IMEM/阵列/DMA/缓存） | 0.59M | 0.15M | 0.44M |

## 4. 实施顺序与依赖

| 阶段 | 内容 | 工作量 | 依赖 | 出口门 |
|---|---|---|---|---|
| P0 | 先测量：把“标量算法”再拆成主机拷贝/描述符/纯算法；`fe_load` 改 DMA；描述符模板复用；批量 SPAD DMA API | S | 无 | 功能不变，总周期 −8–12% |
| P1 | A1：`dft200_bluestein` / `dft360_bluestein`，接 `equalise_demap` 与 `modulate` | M | P0 的 DMA 封装 | 逐值对齐；两个 PUSCH 场景阶段周期达标 |
| P2 | A2：spad 旋转表 RTL + block-major + CN/BN 融合 + bank swizzle | L | P0；RTL 回归 | 1040/1040、80/80、≤120 runs/块 |
| P3 | A4 + A5：Turbo kernel、QAM/加扰 kernel | M | P0 | BER/逐符号一致 |
| P4 | B1.2/B2：64-bit 主机口、复合任务描述符、done FIFO | M–L | P2/P3 的接口需求冻结 | `verify full`、Fmax ≥ 1.0 GHz |
| P5 | A6：Polar/SSS/WiFi/小区搜索 | M | P1 的 FFT/相关复用 | 各场景阶段周期达标 |

排序理由：

- P1 最大、无 RTL 风险，先拿收益，建立“下沉后确实更快”的信心。
- P2 必须改 RTL，且会碰所有 kernel 的地址语义，放在 P1 之后、P4 之前，独立回归。
- P4 的 64-bit/任务链要等 P2/P3 把接口需求定清楚，避免白改。
- P5 复用 P1 的 FFT/相关基础设施，最后做。

## 6. 验收与风险

### 6.1 验收门（每个阶段都必须全过）

1. **逐值正确**：新 kernel 对 Python 黄金模型逐位/逐符号一致；软值允许 ±1 LSB 的地方要单独标注。
2. **协议门**：对应 `run-proto-*` 判据全过；`make proto-check` 通过。
3. **全量回归**：`bash tools/verify.sh full` 保持 83 passed / 0 failed。
4. **周期门**：本方案第 5 节的阶段目标；偏差 > 20% 要分析并更新估算。
5. **硬件门**：综合 Fmax ≥ 1.0 GHz；旋转表/64-bit 口带来的面积增量 < 5%；`docs/08` 的 PPA 数字同步更新。

### 6.2 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 旋转表改动 spad 地址语义 | 所有 kernel 回归 | 先做开关（`ROT_EN`），默认关闭；逐 kernel 打开；`verify full` 每步跑 |
| Bluestein 定点缩放与现有 DFT 不一致 | LLR/硬判偏差 | 先用 float 模型对拍，再定 Q 格式；允许软值 ±1 LSB，硬判必须一致 |
| LDPC block-major 改动大 | 现有 5 个 LDPC 基准全挂 | 先在 `run-pdsch-iter` 单点验证，再推广到 BG1/Zc64/HARQ |
| bank 冲突不降反升 | 下沉后阵列更慢 | 先做 swizzle 测量，再决定是否加 bank；以 25.5% → <10% 为硬门 |
| 64-bit 主机口时序 | Fmax 下降 | 只在 SPAD/IMEM 窗口加宽，寄存器窗口保持 32 位；综合后看 STA |
| 复合描述符 RTL 复杂 | 调度死锁/兼容性 | 保留现有 ring 作为 fallback；新描述符只走新 ring；加超时/错误位 |
| 估算过于乐观 | 目标无法交付 | 每阶段先做单点 benchmark，再更新第 5 节；以实测为准 |
