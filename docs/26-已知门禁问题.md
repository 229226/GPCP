# 26. 已知门禁问题

## 26.1 `run-pdcch`：SNR 探测下的 Polar 盲检固定错 5 位（未修）

**状态**：`bash tools/verify.sh full` 当前为 **83 / 84**，唯一失败项是
`run-pdcch`。该失败**不是** 2026-11-15 节点粒度 / 复合描述符这一轮引入的：
在 `git worktree add --detach /tmp/gpcp_head HEAD` 的完全干净代码树上，
补齐 HEAD 缺失的 `us_equalise_demap` 兼容入口使其能编译后，同样的
`[FAIL] PDCCH / DCI blind detection acceptance` 稳定复现。

**现象**（`make -C sim/soc run-pdcch`，SNR 8 / 12 / 15 / 20 都一样）：

```
CRC24C did not pass on any candidate
DCI: 31/32 bits differ
polar info: 5/56 bits differ (first [0, 1, 7, 8, 54])
candidate CRC verdicts: hw=[0,0,0,0,0] model=[0,0,1,0,0]
raw LLR hw=[-1344,-1296,2048,...] model=[-1339,-1295,2056,...]
```

- 翻转位**与 SNR 无关**，是确定性的，不是噪声临界；
- 信息位 0/1/7/8/54 对应 Polar 索引 15/23/79/87/511，即各宽度分组的
  最后一个叶子；中间 46 位全对；
- 原始 LLR 与模型差异 <1%，冻结位集合与 `tools/nr_pdcch.py` 逐位一致，
  `pdcch_luts.h` 与 `tools/gen_pdcch_luts.py` 重生成结果逐字节相同。

**已排除**：RTL 改动（HEAD RTL 同样失败）、`ssb_fft.inc` 的 `DESC_MODE` 写、
`pdcch_bm.bin` 陈旧（强制重编后仍失败）、冻结位集合、LUT、twiddle 表。

**缩小到的范围**：`sw/soc/pdcch_bm.c` 的 `node_run()` 通过 D-cache 写
`ain/bin/bet` 与 `desc[]`，只用了 `fence`，没有写回/失效。做一次
D$ 失效（启动环前，或读 `fb/gb` 结果前）都能把错误从 5 位降到 **2 位**
（`[0, 7]`）；两处都做反而变成 17 位——说明 `csrw 0x7c1` 序列在这个
路径里会丢 CPU 脏数据，不是通用解法。剩下 2 位指向 Polar 节点微码在
分组末 lane 的边界行为，需要单独排查 `polar_node_prog.h` / `node_run()`。

**为什么以前"通过"**：`$(BUILD)/pdcch_bm.elf` 原先只依赖 `pdcch_luts.h`，
改微码头、`ssb_fft.inc`、寄存器头都不触发重编，门禁一直跑的是旧二进制。
本轮已经把这三个头文件加进依赖（同类问题在 `pdsch_full_bm.elf`、
`pdsch_loop_bm.elf`、`pdcch_loop_bm.elf` 上一并修掉），所以真实行为暴露出来了。

**下一步建议**：给 `node_run()` 加一个只写回、不整片失效的 cache clean
原语；再用软件 SC 参考替换阵列节点跑一次，判定剩余 2 位是微码边界还是
固定点舍入。修好前不要把这个门禁的失败算到协议链路性能结论上——
17 个 `run-proto-*` 场景、`run-pdcch-loop`、`run-pdsch-loop` 都是绿的。
