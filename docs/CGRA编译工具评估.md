# CGRA 编译工具能力评估与内核边界方案

日期：2026-11-18
背景：目标是用 bsim 的 Python 程序作为 GPCP 的性能基准。bsim 侧不写任何架构信息，内核识别、定点化、映射全部由编译器完成。本文回答两个问题：内核边界怎么定、现有开源 CGRA 工具能复用哪些部分。

## 1. 内核边界：bsim 不标注，由编译器判定

bsim 源码里没有任何 `@kernel`、pragma 或注释级标注。唯一的 "kernel" 字样是导出 JSON 里的字段名。

编译器侧（`cgracc static`）已经能自己判定：

| 函数 | 判定 | 依据 |
|---|---|---|
| `mmse_detect` | 可下沉（需降低） | 纯函数、固定形状、只用算术/复共轭 |
| `mmse_via_weight` | 可下沉（需降低） | 同上 |
| `make_case` | 主机 | 随机源 |
| `export` | 主机 | 文件 I/O、字典、动态追加 |
| `run` | 主机 | 循环边界为运行时参数 |
| `main` | 主机 | 命令行解析、打印 |

```
汇总  可下沉 2 / 主机 4
调用边界  run (主机) → mmse_detect (下沉)；run (主机) → mmse_via_weight (下沉)
```

`--function mmse_detect` 只是"查看某个函数的编译结果"的调试入口，不是源码标注。要彻底去掉人工选择，加 `compile --auto`：编译器扫描全文件，对所有 `static-lowered` 函数逐个编译。M1 的输出已经包含全部所需信息。

## 2. 输入 C 与架构是否相关

**架构参数不在 C 里，但 C 不是随便写的普通程序**——需要内核边界标注，并落在可静态分析的子集内。

| 工具 | 输入 C 的真实要求 | 架构信息在哪 |
|---|---|---|
| CGRA-ME | C/C++，用**用户标注**圈出提 DFG 的区域；不支持嵌套循环，条件码支持有限 | CGRA-ADL 架构描述 |
| CGRA-Flow | C/C++ 的**循环内核**，MLIR 前端 | 架构配置文件 + 编译器 legalize |
| Morpher | **带标注的 C**，DFG 生成器从标注区域提取 | ADL + 映射器 |
| NEURA | C 内核，转成纯 dataflow IR | 可重定向后端 |

三类常被误以为写在 C 里、实际由编译器决定的东西：

1. 位宽/数据类型——源码可写 `float`，后端 legalize 到 32-bit 整数；
2. 存储层次——源码没有 spad/DMA/page，由内存规划决定；
3. 并行度/PE 数/连接——全部来自架构描述。

真正与"架构无关性"冲突的只有两点：**内核边界**（需要标注或约定）和**可静态分析性**（循环边界可知、无动态分配、无指针追逐）。

## 3. 能力对照：我们需要什么 vs 它们给什么

| 需求 | CGRA-ME | Morpher | CGRA-Flow | NEURA | 判断 |
|---|---|---|---|---|---|
| 吃普通 Python 源码 | ✗ | ✗ | ✗ | ✗ | 需自己写 |
| 自动判定内核（无标注） | ✗ 需标注区域 | ✗ 需标注 | ✗ 需循环内核 | ✗ | 我们的 M1 更靠前 |
| 从源码提 DFG | ✓ LLVM | ✓ | ✓ MLIR | ✓ | 可参考，但输入是 C |
| float→定点 | ✗（靠 TAFFO） | ✗ | ✗ | ✗ | 空白 |
| 除法/超越函数 legalize | 部分 | ✗ | 部分（32-bit legalize） | 部分 | 部分 |
| DFG→PE 映射 + 调度 + 路由 | ✓ | ✓ | ✓ | ✓ | 最值得借 |
| 周期精确仿真 | ✓ | ✓ | ✓ | ✓ | 可参考 |
| 架构描述能否写 GPCP | 需评估（ADL） | 需评估（异构 ADL） | 需评估 | 需评估 | 成本点 |
| 输出 GPCP 微码 | ✗ | ✗ | ✗ | ✗ | 需自己写 |

结论：

1. 它们补的正是当前最弱的一环——把 DFG 的每个节点独立映射到 PE（含私有寄存器、路由、modulo 调度）。`cgracc` 现在是"一个连通分量绑一个 PE"，这是 286 拍只用 1 个 PE 的根因。
2. 它们补不了 Python 前端、自动内核判定、浮点定标、微码格式。这些恰好是 M1/M2 已经做出来的部分。
3. 不建议整体接入：写 GPCP 的 ADL 并适配 IR 的成本，可能高于在现有 `cgracc` 上补一个真正的空间映射器（schedule/check/emit/conformance 已具备）。

## 4. 实施路线

M1 可静态化判定 → M2（Python AST）与 M2'（clang IR）前端生成 DFG → M3 mesh 路由与重调度（已完成，见第 5 节）→ 下一步批量吞吐。全程不接入外部框架。

## 5. M3 实测：C 源码 → mesh 路由 → 周期

工具评估之后的实际路线：不接 CGRA-ME，用 clang 做前端、自研 mesh 路由。

### 5.1 前端（clang，不写解析器）

`cgracc compile-c` 调 `clang -S -emit-llvm -O1`，只消费优化后的 SSA 标量 IR：

| 输入 | 产出 |
|---|---|
| `bsim/c/mmse.c`（普通 C，零硬件信息） | 184 节点 DFG：mul 57 / shr 57 / add 32 / sub 14 / ld 18 / max 2 / st 4 |

降低规则全在编译器：`complex → 实虚两路`、`float → Q15`、`fdiv → Newton 倒数`、`fmuladd → mul+add`。

### 5.2 互连契约

`arch/gpcp_4x4/model.yaml` 新增 `interconnect`（真相来自 `cgra/target.yaml` 与 CGRA-ME ADL）：

```yaml
topology: mesh, rows: 4, cols: 4
ports: [north, east, south, west]
hop_latency: 1
source: register_only      # 跨 PE 只能读邻居的寄存器输出，禁止组合直通
link: {writer: macl, latency: 1}
```

编译器侧提供 `neighbors(unit)`，检查器新增 **R11**：跨 PE 必须相邻且满足 hop 延迟。

### 5.3 两阶段路由

| 阶段 | 做法 |
|---|---|
| 粗映射 | 拓扑序贪心；优先选「能同时读所有输入的 PE」（同 PE 或邻居），累计负载轻者胜 |
| 路由 | 每个源做一次 BFS 最短路树，只建用到的分支，逐跳插 `mov`（1 拍） |
| 重调度 | `MeshScheduler(fixed=...)` 按已定 PE 排 cycle，检查寄存器/发射冲突 |

### 5.4 结果

`mmse_2x2`，500 条测试向量：

| 方案 | 节点 | 拍 | 关键路径 | 检查 |
|---|---|---|---|---|
| 单 PE 串行（list） | 184 | 184 | 31 | 0 |
| spad 中转（split=1） | 508 | 204 | 89 | 0 |
| **mesh + 路由** | 309 | **96** | 47 | **0** |
| 理论下界（关键路径） | — | 47 | — | — |

数值 EVM 0.135%（与浮点参考一致）；`conformance 10/10`。

### 5.5 粗映射的三个版本（负结果）

| 策略 | mov | 拍 | 结论 |
|---|---|---|---|
| 覆盖优先 + 累计负载 | 125 | **96** | 最优，已采用 |
| 活跃值生命周期（引用计数释放） | 80 | 101 | 路由少了，但节点挤进 8 个 PE，发射槽成瓶颈 |
| 活跃值 + 每 PE 硬上限 | 117 | 112 | 分散过头，路由暴涨 |

实测最忙的 PE 有 65 个节点（>关键路径 47），说明瓶颈是**发射槽**而非路由；让后 8 个 PE 参与就要跨更远，两者此消彼长。

### 5.6 结论与下一步

- 单 RE 的图宽只有 5.9，96 拍已到"关键路径 × 2"以内；
- 继续压单 RE 收益有限，**唯一显著提升吞吐的是批量**（N 个 RE 并排，吞吐 ×N）；
- 若要再降延迟，需要更细的路由共享（多源树合并）或允许 2 跳直读。

## 6. M4 / M5：微码闭环与自动切段

### 6.1 M4：直接发 IMEM 微码并闭环验证

`compile-c --emit` 的输出是与 `sw/soc/gen/*_prog.h` 同格式的 C 头文件，
再用 `frontend/imemsim.py`（按 `cgra_pe.sv` 的时序语义复刻）把这条微码
真正跑一遍，与 DFG 解释器的结果比对，两者必须完全一致。

| 内核 | 调度（拍） | 指令数 | IMEM EVM | DFG EVM |
|---|---|---|---|---|
| `eq_test` | 50 | 11 | 0.000% | 0.000% |
| `fft8` | 50 | 20 | 0.003% | 0.003% |
| `mmse_2x2` | 143 | 100 | 0.019% | 0.019% |
| `dot64` | 299 | — | 0.107% | 0.107% |

> 上表是 M4 阶段（统一 Q15）的基线。M6 改成按区间自动定标后拍数与 EVM 都变了，
> 见 6.3；其中 Q15 基线的数值依赖“乘法操作数不做 16 位截断”，在真机上并不成立。

过程中确认了三条 RTL 事实，并据此改掉了依赖它们的设计：

1. **link 寄存器只保存上一拍写寄存器的结果**（`if (wr) link_wr=1`），不是持久寄存器；
   跨 PE 的长延迟值必须走 spad 中转，`mov` 链的写法是错的。
2. 邻居端口读的是**对方上一拍**的 link；生产者在西边要用 `w` 口读、东边用 `e` 口读。
3. `ld` 从 spad 取数，操作数选择器不参与编码（`src_a=src_b=zero`）。

### 6.2 M5：装不进一次 run 就自动切段

一次 run 最多 512 拍，且没有硬件循环/分支。关键路径超过上限时任何映射都装不下，
只能切段：按依赖深度切开，跨段值在前段 `st`、后段 `ld`，主机按顺序装载并启动
每一段（spad 与寄存器跨 run 保持）。头文件导出 `*_PROG_SEGMENTS`、
`*_seg_cycles[]`、`*_seg_offset[]`，主循环照着注释跑即可。

硬约束：段间传递区是 spad 的 6 KB～8 KB 段，跨越段的值超过约 500 个就放不下，
会明确报错而不是静默溢出。

`dot256`（256 点内积，1285 节点）在 M5 阶段实测：

```
分段  4 段 [282, 264, 260, 288] 拍，共 1094 拍（单段上限 512，关键路径 208 拍）
      s0 切在深度 64（1085 节点，197 个跨段值）
IMEM  4 段 模拟 4 条，EVM 0.297%    数值 4 条，EVM 0.297%
```

（M6 重新定标后为 4 段 1167 拍、EVM 0.002%，见 6.3。）

顺带修掉两个**映射质量**瓶颈（与切段独立）：

- 调度顺序从 FIFO 拓扑序改成**深度优先后序**：FIFO 会把 513 个 `ld` 全排在最前，
  输入值同时活着，8 个寄存器的 PE 必爆；DFS 让中间值紧挨消费者发射；
- **`ld` 贴近消费者**：spad 随机读，什么时候读都行，后处理把每条 `ld` 推到
  消费者前一拍，几百拍的活跃期直接消失。

后来在 M6 又补了一条切段判据：**寄存器装不下也切段**。`dot256` 切在深度 64 时，
第 0 段在 283 拍内装得下（上限 512），但 PE12 从第 30 拍到第 110 拍指令排满，
`ld` 无法再贴近消费者，第 67 拍有 9 个值同时活跃。现在切段前会先试跑一次
寄存器分配，失败就把该段按深度再切一半（`dot256` 因此从深度 64 改切在 32）。

### 6.3 M6：按区间自动定标

统一 Q15 有两个问题：动态范围不够（|x|≤0.5 的输入只要 Q16，256 项累加要 Q30），
以及违反硬件约束——`rtl/cgra/cgra_pe.sv` 的乘法是

```systemverilog
assign prod = sx16(val_a) * sx16(val_b);
```

乘法操作数只取低 16 位有符号数（-32768..32767）。Q15 下常量 `4.0` 是 131072，
作为乘法操作数会被截成 0，所以旧基线在真机上根本不可实现。

现在每个值都携带一个区间 `[lo, hi]`，逐级传播：

1. **输入**：用测试向量按元素统计区间；**常量/载入值**按“能直接当乘法操作数”定标
   （上界 ≤32767 时用 `floor(log2(32767/bound))`），否则按 32 位安全余量定标；
2. **加减/选择**：先把两个操作数对齐到同一 Q，若结果可能溢出 32 位就整体降 Q；
3. **乘法**：操作数先按需 `shr` 到 ±32767 以内，乘积 `q = qa + qb`，
   再按 32 位余量下移；乘积的 Q 因此天然高于操作数；
4. **除法**：展开成 Newton 倒数 `x ← x(2-bx)`（两次迭代），用 `1/b` 的解析界收紧
   迭代区间，残差 step 取保守的 `[0.25, 3]`；
5. **输出/`st`**：每个 spad 地址记录自己的 Q，主机按地址还原。

**两遍（profile 引导）定标**：第一遍用区间传播的结果定标，跑测试向量并记录每个
语义节点的**实测**区间（留 2% 余量），第二遍用实测区间重新定标。这一步是必需的：
`mmse` 的 `det = a00*a11 - |a01|²` 两个相关项相减，推导区间宽到 `[-1, 1.29]`，
迫使倒数初值区间到 `[0.39, 32]`，乘法操作数被压到 Q9；换成实测区间后 EVM 从
0.177% 回到 0.010%。

当前结果（`--route`，IMEM 闭环）：

| 内核 | 节点 | 拍数 | 定标范围 | IMEM EVM |
|---|---|---|---|---|
| `eq_test` | 71 | 55 | Q0…Q30 | 0.000% |
| `fft8` | 110 | 51 | Q15…Q29 | 0.004% |
| `mmse_2x2` | 208 | 163 | Q12…Q30 | 0.010% |
| `dot64` | 321 | 304 | Q15…Q30 | 0.002% |
| `dot256` | 1285 | 4 段 1167 | Q15…Q30 | 0.002% |

对比 M5：`dot64` 从 0.107% → 0.002%，`dot256` 从 0.297% → 0.002%，
`mmse` 0.019% → 0.010%（且旧值在 `sx16` 语义下不可实现）。代价是中间值需要
对齐/缩放，节点数略增（`dot256` 从 1282 → 1285，多出的 `shr` 用于乘法后定标），
`dot256` 因寄存器压力多切一刀，总拍数 1094 → 1167（+6.7%）。

### 6.4 M7：整文件扫描与主机/内核划分

`compile-c --auto` 不再需要 `--function`：扫一遍 clang IR 里**所有有定义的函数**，
逐个尝试降低。判据只有一条——能不能把这份 SSA IR 完整变成 DFG：

- 能 → 内核，自动切成若干段并发射微码；
- 不能 → 主机函数，失败原因（第一条不支持的 IR 指令，如 `call`、`alloca`、
  未展开的 `phi`/`br`）就是判据，同时列出它调用了哪些同文件函数，即主机→内核的
  调用边。源码里没有任何 kernel 标注或坐标。

调用约定由编译器生成并导出到同一个头文件，主机不写死任何地址：

| 导出 | 含义 |
|---|---|
| `<K>_IN_P<n>_BASE / _WORDS` | 第 n 个数组参数的输入基址与字数 |
| `<K>_OUT_P<n>_BASE / _WORDS` | 输出基址与字数 |
| `<K>_SCALAR_BASE / _WORDS` | 标量参数区 |
| `<k>_in_p0_q[]` 等 | 每个地址的 Q（主机按 2^-Q 量化/还原） |
| `<K>_seg_offset / _seg_cycles` | 每段的装载偏移与拍数，按序启动 |

参数与返回值全部经 spad 传递（无寄存器传参、无栈、无跨调用保活）；多内核共用一个
头文件，符号与宏都带内核前缀，互不冲突。

实测：

| 输入 | 判定 | 结果 |
|---|---|---|
| `bsim/c/mmse.c` | 1 内核（`mmse_2x2`），0 主机 | 208 节点 / 163 拍，IMEM EVM 0.010% |
| `cgracc/examples/dot8.c` | 6 内核，0 主机 | 一个头文件，`dot256` 自动切 4 段 |
| `bsim/c/main.c` | 0 内核，3 主机（`main`/`on_off`/`selftest`） | 主机 `selftest` 的调用边里含 `mmse_2x2` |

`mmse.c` 的自动扫描结果与 `--function mmse_2x2` 单函数路径逐位相同（208 节点 /
163 拍 / 0.010%），说明扫描没有改变编译结果；生成的头文件用
`clang -std=c11 -fsyntax-only` 校验通过。

### 6.5 M8：运行期下标

硬件没有间接寻址：`ld`/`st` 的地址是立即数，也没有分支和谓词写。所以运行期下标
按「硬件能做什么」分开处理：

| 形态 | 编译策略 |
|---|---|
| 常量下标（前端展开后） | 直接变成固定地址 `ld imm` |
| 只读 `a[idx]`，范围有界 | 展开成 `hi-lo+1` 个固定地址读，再用 `idx==k` 的选择链（MUX）串起来 |
| 下标范围未知 | 拒绝：需要测试向量给出取值区间，或同一数组上的常量下标推断上界 |
| 写回 `out[idx] = x`（scatter） | 拒绝：`st` 不可谓词化，整函数留给主机 |

整数标量（如 `long idx`）按 Q0 传递原始整数，头文件导出 `<K>_scalar_q[] = {0}`，
主机原样写入、不做定点缩放。

实测 `cgracc/examples/pick8.c`（`pick8` = `out[0] = a[idx]`，`scatter8` = `out[idx] = x`）：

| 项 | 结果 |
|---|---|
| 判定 | `pick8` 内核、`scatter8` 主机（原因：scatter 没有硬件支持） |
| 节点 | 74（8 个固定地址读 + 7 组比较/选择） |
| 拍数 | 109（关键路径 77） |
| IMEM | 8 条向量，EVM 0.003% |

下标区间来自测试向量的实测值（0..7）：第 1 遍没有向量时先按 [0,0] 编出来跑
profile，第 2 遍拿到真实区间后重编，和 M6 是同一套两遍流程；没有向量、也没有常量
下标可推断上界时，编译器明确拒绝而不是猜一个地址。

M1–M8 至此全部落地。再往下不是流程问题，而是硬件能力问题：要支持真正的间接寻址
或 scatter，需要给 `ld`/`st` 加寄存器地址或谓词写。
