# 14. CGRA 编译器方案（程序 → 微码）

> 目标：把「新算法 → 手写 78 行 `Program.set(cycle, pe, ...)`」变成「写一段受限 C，一条命令出微码」。
> 本文所有约束都来自已实现的 M0 硬件（`docs/02-cgra-isa.md`），不是纸面设计。

## 0. 为什么现在做

| 事实 | 数字 |
|---|---|
| 手写微码 kernel | **16 个 / 1250 行**（`tools/cgra.py`），平均 **78 行/个** |
| 每个 kernel 还要额外写 | 黄金模型、spad 布局、预装载表、寄存器分配 |
| P5–P8 预计新增 | SRS、PUCCH fmt 2/3/4、2-step RACH、LDPC BG1、CSI 多配置 —— **至少 10 个** |
| 手工映射的错误定位成本 | 微码错与 RTL 错在 dump 里长得一样，只能靠人肉二分 |

边际成本不随数量下降，这就是"重复造轮子"里最贵的那一个。

## 1. 先盘点：这些已经存在，不要重写

| 资产 | 位置 | 在编译器里的角色 |
|---|---|---|
| ISA 编码 `enc()` / `Program.set(cycle, pe, …)` | `tools/cgra.py` | **唯一**编码定义，直接复用 |
| 周期精确 ISA 仿真 `simulate()` | `cgra/tools/rule_map.py` | 编译器的**正确性 oracle**（已在用） |
| DFG 表示 + 规则调度 + 寄存器线性扫描 | `cgra/tools/rule_map.py` | 后端起点（v0 已能编 LDPC BN/CN） |
| 16 个手写 kernel | `tools/cgra.py` | 差分测试的黄金参考 |
| Python 黄金模型 | `tools/nr_*.py` | 数值对拍 |
| 回归门 + 输入指纹缓存 | `tools/verify.sh` | 端到端验收 |

**`rule_map.py` 已经是一个"迷你编译器"**：DFG → 微码 + 自带 ISA 仿真逐位自检。
它自己写清了四项未做，这正是本方案要补的全部内容：

1. 无 link 路由（跨 PE 通信只能走 scratchpad，慢且占 bank）；
2. 无跨 PE 算子共享；
3. 无 PE 内多拍流水重叠（一条指令 = 一拍，串行）；
4. 无寄存器 spill。

## 2. 目标与非目标

**目标**
- 输入：受限 C（定长 `for` + 数组 + 定点算术）**或** Python DSL（直接构 DFG）；
- 输出：`Program`（VLIW 微码）+ spad 布局 + **主机编排**（DMA 描述符序列）+ `cycles`；
- 硬约束：单段 ≤ **512 拍**（IMEM 8192 字 / 16 PE）、每 PE **8 个寄存器**、`LD/ST` 10 位地址、
  每 PE 每拍 1 条指令；
- 性能目标：首版放宽到 `cycles ≤ 手写 × 1.3`，M3 收敛到 `× 1.1`；
- 编译时间：单 kernel **< 1 s**（能塞进 `make` 循环），改一行 C 的增量 < 0.5 s。

**非目标（明确不做，避免过度工程）**
- 通用 C：指针算术、递归、动态内存、函数指针；
- 完整多面体优化（只做 affine 循环的 tiling）；
- 8×8 的分层互连（等 RTL 演进后再扩，MRRG 天然可扩）；
- 自动数值优化（定点位宽推导）——先要求用户显式标注 Q 格式。

## 3. 流水线

```
 kernel.c / DSL
      │ 前端：AST → DFG（算子级，含循环结构与 affine 下标）
      ▼
   DFG + 循环信息
      │ tiling：迭代空间 → (PE 空间并行) × (时间流水)
      ▼
   分层 DFG（每层 = 一个 II 内可并行的算子集合）
      │ 调度：II 搜索 1..8，资源约束 = 16 PE/拍
      ▼
   (算子 → (pe, t))      ←──────┐
      │ 放置：模拟退火，代价 = Σ曼哈顿距离 + 拥塞
      ▼                          │ 失败：rip-up & reroute
   (算子 → 固定 pe)
      │ 路由：XY + 协商拥塞（PathFinder）
      ▼                          │ 失败：II+1 / 降级走 spad
   (边 → 每拍每 PE 的 link 路径)
      │ 寄存器分配：活跃区间 + 8 寄存器，溢出改走 spad
      ▼
   微码打包（cycle × 16 PE）→ *_prog.h + sched.json
      │
      ▼
   验证：ISA 仿真 ⇄ 黄金模型（逐位）→ 影子模式接 run-*
```

## 4. 关键设计决策

**D1 用 MRRG 建模空间/时间资源，而不是"先排时间再摆位置"**
MRRG（Modulo Routing Resource Graph）：节点 = `(pe, t mod II)`，边 = 4 方向 link / 寄存器 /
spad 端口。一个 DFG 可映射 ⇔ 存在同态子图。这样放置与路由在同一个代价函数下联合优化，
避免了"先贪心摆放、后面路由全冲突"的典型失败。

**D2 II 从 1 起搜，但必须有"降级路径"**
4×4 只有 16 个 PE，复杂 kernel 的 II 可能到 3–4。若 II 超过上限或路由失败，
**降级为"经 scratchpad 中转"**（相当于 rule_map v0 的行为）：性能下降但保证有解。
编译器永远不因"排不下"而失败——这是可用性底线。

**D3 路由用 XY + 协商拥塞**
每 `(cycle, pe, direction)` 容量为 1。XY 先给确定性路径，冲突时用 PathFinder 的历史拥塞代价
做 rip-up。中间 PE 用 `MOV dst, <neighbor>` 转发，天然利用 link 的 1 拍延迟。
**MAC 不更新 link**这一特性要主动利用：移位拍与累加拍可以相邻而不互相破坏。

**D4 寄存器：图着色，link 不算寄存器**
活跃区间 = `[def, last_use]`，8 个寄存器；`acc` 单独算。溢出时把值降级到同一个 spad word
（有明确代价：+2 拍 + 1 bank）。**禁止**静默 spill——必须在 `sched.json` 里报告。

**D5 分段是一等公民**
IMEM 只能装 512 拍，FFT256 这类 kernel 必须切成多段，段间用 descriptor ring 双缓冲。
编译器必须**自己决定切段位置**（按数据依赖的天然边界），并输出每段的
`cycles / preload / spad 布局 / 段间依赖`，而不是让程序员手工切。

## 5. 核心算法要点

- **MAC 链识别**：`acc += a*b` 且 `acc` 无其他消费者 → 发射 `MAC` 而非 `MUL+ADD`（省 1 拍 1 寄存器）；
  若结果要沿链传给邻居 → `MACL`。
- **算子复制**：当一个值有 >2 个跨远距离消费者时，复制算子比长距离路由便宜（≤ 2 跳内不复制）。
- **spad 布局**：叶子按 `bank = 输入序号`、`word = 实例号`（与现有 BN 布局一致，便于对拍）；
  编译器输出布局表，供主机侧 DMA 描述符生成。
- **边界输入**：`PE(0,0)` 的西边界是 `din` 流；编译器可把"流式输入"映射到这条路径，
  省掉一次 spad 往返（FIR/相关器类 kernel 收益最大）。

## 6. 前端范围（受限 C）

支持：
```c
void k(const short *x, int *y) {          // 定长、无指针算术
  for (int i = 0; i < 16; i++)            // N 为编译期常量
    y[i] = (x[i] * tw[i]) >> 15;          // 算术右移 = SHR
}
```
- 类型：`short`(int16) / `int`(int32)，Q15 显式；
- 运算：`+ - * >> << & ^` 与 `max/min`；
- 下标必须 affine（`a*i + b`）；
- 数组大小、循环上界必须是编译期常量。

**降级规则**：遇到不支持的结构 → **报错并给出行号**，绝不静默生成错误微码。
这条比"支持更多语法"重要得多：错编译比不编译危险。

## 7. 主机编排（最容易被漏掉的一半）

微码只算数，数据得先搬进 spad、结果得搬出来。编译器同时输出：

```json
{ "segments": [
    { "prog": "fft_s0", "cycles": 96, "buf_page": 0,
      "dma_in":  [{"src":"ram+x", "dst_bank":0, "len":256, "stride":32, "row":8}],
      "dma_out": [] } ],
  "spad_layout": {"x": [{"bank":0,"word":0,"len":8}], "y": [...]} }
```

- 自动生成 descriptor ring 序列与 `buf_page` 翻转（ping-pong 双缓冲）；
- 段间依赖自动插入"等 `RING_DONE`"的同步点（复用现有 `run-slot` / `run-ring` 的机制）；
- 没有这一层，编译出的微码**跑不起来**——这也是手工 kernel 每写一个就要配一套 host 代码的原因。

## 8. 验证：三级 + 影子模式

| 级别 | 做法 | 抓什么 |
|---|---|---|
| L1 编译期 | `rule_map.simulate()` 跑微码 vs Python 黄金模型，**逐位** | 调度/路由/定点语义错 |
| L2 差分 | 同算法：编译器产物 vs **16 个手写 kernel**，逐位相同 | 编译器与既有实现的偏差 |
| L3 端到端 | **影子模式**：生成 `*_prog_cc.h`，与手写版并存，`run-*` 各跑一遍比对 | 与真实 RTL/时序的差异 |

**影子模式是关键**：绝不一次性替换手写微码，否则 54 个门同时挂，无法定位是编译器还是硬件。
`KERNEL_SRC=hand|cc` 一条开关切换，只有当某个 kernel 的 cc 版本连续 N 次全绿才切默认。

## 9. 里程碑（每步都有可验收的数字）

| 阶段 | 内容 | 验收 | 估计 |
|---|---|---|---|
| **M0** | `tools/cgra_cc.py` 最小闭环：DFG → 微码（复用 `rule_map` 调度）+ CLI + Makefile 规则 | 编译 `matmul4x4`，与手写微码**逐位相同**；< 0.2 s | 3 天 / `infra` |
| **M1** | MRRG + 放置（退火）+ XY 路由 + 算子复制 | 编译 `fft16` / `chnest`，逐位相同且 `cycles ≤ 手写 × 1.3` | 1 周 / `arch`+`infra` |
| **M2** | 受限 C 前端（pycparser）+ 自动分段 | 从 `.c` 编译 `fft_stage`（>512 拍自动切段），`run-fft` 端到端绿 | 1.5 周 / `infra` |
| **M3** | 模调度/流水 + 主机编排（descriptor ring） | 编译 PDSCH 接收链（chnest→MMSE→LDPC），接入 `run-pdsch-full` | 2 周 / `infra` |
| **M4** | 8×8 迁移（分层互连进 MRRG） | 与 RTL 演进同步 | 随 RTL |

每阶段结束必须更新：`cycles` vs 手写、编译时间、路由失败率、寄存器溢出次数（写进 `docs/11`）。

## 10. 风险与对策

| 风险 | 后果 | 对策 |
|---|---|---|
| 512 拍上限 | 大程序必须切段，段间 DMA 开销可能吃掉收益 | 切段位置按数据依赖选；段数>8 时报警 |
| 路由冲突 | 编译时间爆炸或排不下 | 协商拥塞 + 明确降级到 spad，**永不编译失败** |
| 定点语义偏差 | 硬件与模型对不上，误判为 RTL bug | L1 必须逐位；`>>` 一律算术右移；Q 格式显式 |
| 编译器 bug 伪装成硬件 bug | 排查成本极高 | 永远先跑 ISA 仿真再看 RTL；影子模式并行 |
| 一次替换太多 | 54 个门同时挂 | 影子模式 + `KERNEL_SRC` 开关，逐 kernel 切换 |

## 11. 与"重复造轮子"的关系

上一个审计（`docs/13`）里最贵的一类重复是**结构性**的：每个新门都复制一份骨架。
编译器是这一类重复的**根解**——它让"新算法"不再需要手写 78 行映射，
而是写 5 行 C。16 个 kernel × 78 行的存量，就是它的收益上限；P5–P8 的 10+ 个新 kernel 是它的收益实现。

**建议的上手顺序**：先做 M0（3 天，只接 DFG 不接 C），当天就能验证"编译器产物 = 手写微码"；
有这条 bit-exact 基线之后，再上路由和前端。反过来（先做前端）会在没有正确性保证的情况下堆功能。
