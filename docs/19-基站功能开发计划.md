# 19 — 基站（gNB）功能开发计划

> 目标变更（2026-11-08）：从「把 UE 侧 L1 做全」转为「把一套能工作的 gNB 做完」。
> 本文件取代 `docs/11` 的阶段划分（P1–P8），`docs/11` 保留为历史记录。
> 协议依据：38.300（gNB 功能）、38.401（架构）、38.211/212/213/214（PHY）、
> 38.321（MAC）、38.322/323（RLC/PDCP）、37.324（SDAP）、38.331（RRC）、
> 38.413/29.281/23.501（NGAP/N3/会话）。

## 0. 起点：现在的系统是什么

一条 CGRA 加速链，**只做接收**：

- **已具备（硬件、逐位验收）**：gNB 的上行 L1 接收 —— PRACH 检测、PUSCH（CP-OFDM 与
  DFT-s-OFDM）、PUCCH；以及 UE 的下行 L1 接收 —— SSB/PBCH、PDCCH、PDSCH（QPSK/16/64QAM）、
  LDPC BG1/BG2、Polar SC、CSI。
- **只有模型（Python）**：所有方向的**发射波形**（TD 生成器）、MAC PDU 复用与 HARQ 实体、
  RRC（紧凑位域）、功控、REG/CCE 映射、链路自适应。
- **空白**：调度器、RLC、PDCP、SDAP、NGAP/N3/GTP-U、SRS、移动性。

也就是说：**作为 gNB，我们只有「听」，没有「说」；也没有「决定听谁说、什么时候说」。**
下面的里程碑按这个顺序补。

## 1. 里程碑

### G1 — gNB 会发 SSB（最小发射闭环）★ 当前

| 项 | 内容 |
|---|---|
| 协议范围 | 38.212 7.1.1（PBCH 载荷/CRC/Polar/速率匹配）、38.211 7.3.3（加扰/QPSK/RE 映射）、7.4.3（CP-OFDM 调制） |
| 交付 | ① PBCH Polar 编码（N=512）落 CGRA ✅ `run-pbch-tx`；② 速率匹配 + 加扰 + QPSK（CVA6）✅ `run-pbch-pack`（含 38.212 7.1.1 的 CRC24C 可选模式）；③ IFFT + CP 落 CGRA；④ **自环**：SoC 生成 SSB 样本 → 自己的 SSB 接收链解出 MIB |
| 验收 | `run-pbch-tx`（polar 变换逐位）→ `run-pbch-pack`（编码链逐段逐位，K=32/56 双模式）→ `run-ifft`（逐样本 = 浮点模型，误差 ≤1 LSB）→ `run-ssb-tx`（自环 MIB 32/32、N_ID 正确） |
| 为什么先做 | 不需要 LDPC 编码器、不需要预编码；Polar 编码的 9 级微码**已经由编译器生成**但从未上过硬件；IFFT 可以复用现有 FFT 微码（共轭 + 1/N） |
| 口径 | 速率匹配长度 **E=720 / 360 QPSK 符号**（`ssb_plan_p1.py` 的 `2*(240-28)*2` PBCH 数据 RE），不是协议 full-SSB 的 864/432；这样 A4 自环才能接上现有接收链的 `rate_recover_pbch(·, 512)` |

### G2 — gNB 会发 PDCCH/PDSCH（下行数据面发射）

| 项 | 内容 |
|---|---|
| 协议范围 | 38.212 7.2（DCI/PDSCH 的 Polar/LDPC 编码、速率匹配）、7.3（加扰、调制、层映射）、38.211 7.3.2.3（REG/CCE） |
| 交付 | ① **LDPC 编码器**——B1 已落 **CVA6**（`run-ldpc-enc`；实测落阵列不划算）；② 速率匹配（38.212 5.4.2）+ 加扰——B2 ✅；③ QAM 映射 + 层映射/预编码（单层单天线）——B2 ✅；④ PDCCH 的 REG/CCE 交织（复用 `nr_pdcch_reg.py` 模型）——B3 ✅ |
| 进度 | B1 `run-ldpc-enc`（BG1/BG2 × Zc=20/64 逐位 + syndrome 0）、B3 `run-pdcch-tx`（DCI→CRC24C→RNTI→polar 9 级阵列→E=432→加扰→QPSK→REG/CCE，2 RNTI 变体逐值 0 差，18 次阵列运行）、B2 `run-dl-mod`（4 变体 1020 符号逐值 0 差，参数与接收链同口径：`KB=6/ZC=20`、`USABLE=984`、`E=720`、`K0=rv*246`）均已完成 |
| 验收 | `run-dl-tx`：自环——自己发的 DCI 被自己的盲检解出、自己发的 TB 被自己的 PDSCH 链解出（1040/1040 硬判） |
| 依赖 | G1 的 IFFT/CP |

### G3 — 调度器（单 UE）

| 项 | 内容 |
|---|---|
| 协议范围 | 38.321 5.4（DL-SCH/UL-SCH 资源分配）、5.3（HARQ 实体）、38.214 5.1（MCS 选择） |
| 交付 | ① 每 slot 的 DL/UL grant 分配（RB 起点/长度、MCS、NDI/RV）；② HARQ 8 进程状态机；③ MCS 闭环（CQI→MCS）+ OLLA；④ grant 写进 DCI |
| 验收 | `run-sched`：连续 20 个 slot，grant 与缓冲区状态机与模型逐字段一致；人为制造 NACK 时 RV 走 0→2→3→1 |
| 为什么在 L2 之前 | 没有 grant 就没有「按需发送」，L2 的队列无处落地 |

| 项 | 内容 |

### G7 — 多 UE / 移动性 / 上行精化（可选）

SRS 接收、闭环功控进硬件、多用户调度、切换与寻呼、SI 更新。

## 2. 与旧计划的关系

`docs/11` 的 P1–P4 成果全部并入 G1/G2 的「已具备」；P5（上行精化）拆到 G7；P6（L2）成为
G4；P7（核心网）成为 G6；P8（移动性）成为 G7。差别是**顺序**：旧计划从 UE 视角往里补，
新计划从 gNB 视角按「能发 → 能调度 → 能传包 → 能被核心网认」推进。

## 3. 每一步的判据原则（沿用）

- 验收必须是**逐元素对账**，不接受「流程跑通 / 决策正确」；
- 硬件产物必须能指出它由哪个 kernel/微码生成（手写微码只允许出现在编排层）；
- 新门禁进 `tools/verify.sh`，默认档 `smart` 可复现。
