# 25 — CGRA 覆盖率：阵列接管了多少运算量

> 工具：`tools/cgra_coverage.py`（读 `build/proto/compare_all.csv` + 各场景
> `plan-base.json`）。基线：账本 v3（2026-11-14）。
> 指标全在**后端侧**：`where / impl / array_runs` 是 GPCP 的私有概念，
> 不进 wlbench 的 `metrics.json`。

## 1. 为什么不能用"阶段数"算覆盖率

`nr_mimo` 5 个阶段里只有 2 个在阵列上（40%），但这两个阶段占了 **99% 的标量工作量**。
反过来 `wifi_11be` 6 个阶段一个都没上阵列，整链却仍有 1.17×（因为标量实现本身不慢）。

所以"覆盖率"必须按**工作量加权**，而且要同时看"覆盖了"和"覆盖得值不值"。

## 2. 三个口径

设某场景逐阶段 CPU 周期为 $c_i$、CGRA 周期为 $g_i$，落点 $w_i\in\{array, cpu\}$：

| 口径 | 公式 | 回答什么 |
|---|---|---|
| **阶段覆盖率** | $\frac{|\{i:w_i=array\}|}{N}$ | 有多少个算子交给阵列了（最直观，最容易误导） |
| **工作量覆盖率** | $\frac{\sum_{w_i=array} c_i}{\sum_i c_i}$ | 全交给 CPU 的话，多少工作量被接走（**主指标**） |
| **有效覆盖率** | $\frac{\sum_{w_i=array}\max(0,\,c_i-g_i)}{\sum_i c_i}$ | 其中**真的变快**的部分 |

再加两个诊断量：

- **覆盖段加速** = $\frac{\sum_{array} c_i}{\sum_{array} g_i}$ —— 覆盖了的那些阶段平均快多少；
- **未覆盖残余** = CPU-only 阶段按 $c_i$ 排序 —— 下一步该优化谁。

## 3. 两个必须防的坑

**坑一：覆盖了但更慢。** `lte_cell_search` 工作量覆盖 100%，覆盖段加速 **0.24×**，
有效覆盖 **0%**。只报"覆盖率 100%"会得出完全相反的结论。所以有效覆盖率要和
覆盖率一起报，差值就是"无效覆盖"。

**坑二：标着 CPU，内部却在用阵列。** `nr_pusch_tp` 的 `equalise_demap` 落点是
`control-core`，但 CGRA 路径比 CPU 路径快 **9.83×**——因为它在内部调了一次
Bluestein IDFT（阵列）。这类收益不在"声明覆盖率"里，工具单独统计为
**隐藏收益**（判据：标为 CPU 且 $c_i > 1.2\,g_i$）。

三个数加起来正好是 100%：

```
覆盖 94.6% = 增益 82.9% + 剩余代价 11.7% − 负收益 1.0%
另有隐藏收益 2.4%（标为 CPU 但更快，待切分消除）、未覆盖 5.4%
```

## 4. 当前基线（17 场景，按工作量加权）

| 指标 | 值 |
|---|---:|
| 阶段覆盖率 | 27–40%（多数场景） |
| **工作量覆盖率** | **94.6%** |
| **有效覆盖率（增益）** | **82.9%** |
| 覆盖后的剩余代价 | 11.7% |
| 负收益（阵列更慢） | 1.0% |
| 覆盖段加速 | 7.42× |
| 端到端加速 | 6.34× |
| 隐藏收益（待切分消除） | 2.4% |
| 未被覆盖 | 5.4% |

按算子看"还有谁没上阵列"（按 CPU 工作量排序）：

| 算子 | 样本 | 上阵列 | 工作量覆盖 | 覆盖段加速 | 备注 |
|---|---:|---:|---:|---:|---|
| `ofdm_demodulate` | 10 | 9 | 99.5% | 29.5× | 唯一的例外是 wifi（无阵列 FFT） |
| `decode` | 11 | 10 | 98.1% | 2.20× | LDPC 2.3× / Polar 0.54× 拉低均值 |
| `ofdm_modulate` | 4 | 4 | 100% | 18.7× | |

| `correlate` | 7 | 7 | 100% | 1.44× | cell_search 0.24× 拖累 |
| `modulate` / `dmrs` / `map_to_grid` / `transport_block` | 4–20 | 0 | 0% | — | 控制密集，留 CPU 合理 |

### 4.1 切分试点：`nr_pusch_tp`

`equalise_demap` 原来把均衡、360 点 IDFT、解交织+解扰+软解调挤在一个节点里，
`where` 只能填 `control-core`，但内部用了阵列——这就是 23.7% 隐藏收益的来源。

现已拆成三个节点，各自有唯一落点：

| 节点 | 落点 | 周期（CGRA 路径） |
|---|---|---:|
| `equalise`（匹配滤波） | CPU | 14,369 |
| `transform`（360 点 IDFT） | **阵列** `dft360_bluestein` | 313,373（48 次阵列运行） |
| `demap`（解交织/解扰/解调） | CPU | 111,459 |

结果：隐藏收益 **23.7% → 0%**，整链 6.46× → **6.58×**（+1.9%，省掉了阶段边界外的
重复记账），golden 逐位不变。其余 10 个含 `equalise_demap` / `modulate` 的场景
尚未切分，所以全局仍有 2.4% 隐藏收益。

## 5. 怎么用

```bash
python3 tools/cgra_coverage.py                 # 全场景 + 按算子
python3 tools/cgra_coverage.py --json          # 机器可读（进 CI/看板）
python3 tools/cgra_coverage.py --scenario nr_mimo --detail   # 逐阶段 + 残余
```

**读法**：先看有效覆盖率，再看"无效覆盖"和"未覆盖"两块分别是谁：

- 无效覆盖里最大的是 `lte_cell_search`（0.24×）——短相关不该上阵列，应该回到 CPU；
- 未覆盖里最大的是 `equalise_demap`（23.6% 的工作量在 `nr_pusch_tp`）——它内部
  已经偷用了阵列，说明**声明口径本身需要修**，而不是没做优化；
- `decode` 覆盖 98% 但只有 2.20×——LDPC 的贡献被 Polar SC（0.54×）抵消，
  提升点在 Polar 微码。

## 6. 局限（引用时必须带上）

1. **权重是 CPU 周期，不是运算量。** 这些 kernel 的标量周期与 MAC 数近似成正比，
   但控制密集阶段（解扰、映射、CRC）会被高估。要严格按运算量算，需要每个 kernel
   的 OP 计数表（FFT ≈ 5N·log₂N 复乘、相关 = N×假设数、LDPC = 边数×迭代），
   本工具暂时不臆造这些常数。
2. **`where` 是阶段级标签。** 子阶段的阵列使用（`estimate` 里的 FFT、
   `equalise_demap` 里的 Bluestein）只能靠"隐藏收益"间接发现，不能精确归属。
3. **分母不含链开销。** 整链 TOTAL 与逐阶段之和的差（循环/收尾）单独报告，
   不摊进覆盖率——否则小场景会被开销稀释。
